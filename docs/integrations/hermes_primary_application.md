Both use the original `native_application_v1` client and `site_interactive`

closed automatic transport. Fixed selection uses `deepseek-v4.1-flash` for the
initial strict canary. Automatic selection leaves model/provider unset and

inspection and binding. Host-authorized exact selection calls the same immutable
factory's `with_requested_model` before inspection. It uses inspection/binding
v3 and route v2, preserving the concrete original model and a null routed-request
digest. Pool/account selection remains with the original scope/picker/Broker.
The same role capability and credential reference apply
to both transports; neither grants administrator pool visibility. All new source
transports remain unqualified and application permission remains held. The
shipped `application_fabric_modes` remains empty.

The original client accepts only these two additional numeric HTTP endpoints,
alongside its original 127.0.0.1 endpoint. Host names, other aliases, redirects,
foreign paths and arbitrary ports remain refused. The original tunnel owner
must qualify simultaneous role remotes before either new endpoint is live; an
endpoint declaration does not prove the tunnel is installed or connected.

The authenticated native host selects the role's factory after checking its
original SessionAuthority admission. The original admission ID supplies the
APPLICATION operation identity. The retained binding and client survive native
facade reconstruction. Native tool/API-step identifiers are correlation, not
authority. A missing original binding after uncertain execution cannot be
reconstructed as a fresh request.

## Existing-owner enrollment

The native finite installer accepts a closed v9 `service_profile` with the exact
lane/principal/reference above. A role can enroll either a fixed grant or an
explicit route scope with bounded grants. The original plan, private payload,
publication locks, intent and completion receipt commit that mapping. The
original grant parser checks account ownership, route authority and overlap.
Different models may use the same physical account; additional grants do not
create provider-account rows or extra physical capacity. Legacy services and both
Hermes roles load into the same handler and Broker. Enrollment does not rewrite a
completed role's authority to expand its pool or model scope.

Activation needs implementation qualification, an unexpired owner mode record,
the exact capability-manifest relation and the internal credential issued by the
original enrollment. Fixture-qualified mode rows are not runtime authority.
Provider credentials stay in the native provider owner. A native interactive
ticket and selected-worker OAuth do not grant APPLICATION inference.

For each role, the capability-manifest entry uses the transport's capability ID,
its exact internal reference and only that role's lane. The existing mode record
uses the same immutable transport identity, `qualification_ref`, `qualified_until`
and current workload policy. The original factory checks all of these before it
resolves the internal credential. Configuring `qualified=true` elsewhere cannot
override this source's hold.

## Qualification boundary

The exact `1a21d83955993e9c1bc45130445bd8c5b2388238` source passed all 56 tests in
the Hermes APPLICATION owner workflow, run 42341359603, job 128309536305. Tests
reuse the incumbent factory fixture and verify fixed/AUTO role separation,
held-source rejection before credential access, numeric endpoint closure,
protocol selection and original operation identity. Synthetic grants are not
runtime evidence. The current source composition requires its own normal CI.

Mastermind #2155 at `8fdd2f4566af6c0cf81908895c4e7be90526e965` passed the pinned
Hermes v0.23 native 61-case suite, 49 native-host cases, 170 original/successor
tunnel cases and 46 offline cases on each of Python 3.12 and 3.13. These used
GitHub's merge composition `b679980945a2675622a013485738efa251b4a64b` and include
no live provider acceptance. Mastermind #2186's v9 enrollment regression remains
a separate gate; no installed enrollment is inferred from these source results.

Strict scoped pool selection is limited to an already committed singleton
pool scope. Historical fixed selection, null-AUTO v2 and exact-model v3 remain
distinct contracts. A frozen AUTO inspection cannot be reinterpreted as exact,
and a frozen concrete model cannot be replaced. No model constraint may silently
fall back to another route. The original request identity and uncertainty survive facade rebuilds
and timeouts. Local close is not provider cancellation or settlement proof.

The real canary must join one qualified host admission to one eligible physical
account, observe the served model and durable actual usage, enforce the provider
owner's financial boundary, complete a native tool turn, and reconcile a timeout
without a second provider call or tool execution. For the initial included Go
canary, any Extra Usage OFF evidence must come from the provider owner and bind
the actual account, endpoint/configuration generation and fresh headroom. That
boundary is not a measured zero-cost receipt. The APPLICATION owner must also
preserve dispatch-correlated usage, budget commitments and unresolved financial
effects across consumers and models. Unknown cost must not become zero.

No live role enrollment, tunnel activation, native installation or provider call
is claimed by this source proposal. Protected release, account authorization,
usage settlement and final acceptance remain with their existing owners.
