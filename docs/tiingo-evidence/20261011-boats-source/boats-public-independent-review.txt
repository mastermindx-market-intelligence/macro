P2 — Validate relay clocks at receipt, after the awaited fetch

Location: hub/lib/extfeed.js:1064 and :1081, with the rejection at :790.

_runYahooPoll captures nowMs and session before awaiting _fetchRelay, then supplies that old clock to boatsRelaySnapshot. A fetch beginning at t0 can legitimately return a snapshot published at t0+100ms and received at t0+200ms. The parser rejects it because published > t0 and replaces the last-good map with an empty map. This can repeatedly drop genuine current quotes during normal concurrent publishing. A session boundary crossed during the await also uses the old session decision.

Required repair: take the validation/receipt clock and session after the awaited fetch, while retaining strict rejection of clocks actually in the future at receipt. Add a deferred-fetch regression in which time advances and a snapshot is published between request start and response receipt; it must be admitted. Preserve rejection of a publication timestamp later than the receipt clock.

P2 — Older browser responses can restore a trade after a newer invalidation

Location: terminal/components/TerminalShell.tsx:2779-2807.

pollExtQuotes has no in-flight serialization or request-order acceptance guard. Timer, visibility and symbol-change-triggered requests can overlap. Request A obtains a positive BOATS trade; request B obtains the later post-break or terminal-invalidation response containing the symbol as null and completes first. When A finishes afterward, its trade may still satisfy the 30-second clock checks, so it overwrites the newer null. The expiry timer bounds the damage but does not preserve the invalidation. Checking only capture/gen presence cannot order a null response.

Required repair: serialize/coalesce polling or give all polling triggers one monotonic request-order acceptance guard. An older callback must not overwrite an already accepted newer response, including null. Preserve unmount and symbol-set handling. Add a reversed-completion test with both responses inside the age window: newer null first, delayed older positive second, final display remains null.

P2 — Full relay replacement has no envelope-order barrier

Location: hub/lib/extfeed.js:780-815 and :1081.

The relay parser returns only a Map, and the caller replaces the relay cache without retaining the accepted envelope's publication/capture/generation metadata. Capture and generation are validated and copied onto positive entries, but they do not constrain subsequent replacement; an empty replacement loses them altogether. After accepting a newer B-removal, gap or ended snapshot, any older still-time-valid connected snapshot restores its positive entries. A generation regression is likewise accepted. This trigger requires an older object response to reach the consumer; the source code provides no defense if it does. Sequential polling and no-store reduce occurrence but do not implement the required invalidation ordering contract.

Required repair: retain accepted envelope ordering independently of positive rows, enforce monotonic publication/generation semantics within a capture, preserve terminal/gap invalidation barriers, and define a conservative transition to a new capture so a delayed retired capture cannot regain authority. UUID lexical ordering is not chronology. A malformed fetched envelope should continue to fail closed without erasing the trusted ordering barrier. Add positive -> newer empty -> older positive and newer generation -> older generation tests; neither may resurrect the older trade. Do not discard normal newer valid full replacements.
