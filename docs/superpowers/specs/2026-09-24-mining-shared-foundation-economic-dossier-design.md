## 1. User outcome and the material change

The investor must be able to move from a Mining-related theme to the exact product, operation and business mechanism affected by a development, then understand which company receives the economics, what capital and contractual obligations intervene, and what evidence would invalidate the thesis. The machine must preserve those distinctions so later research does not reconstruct the industry from company labels. The eventual moat is correction-aware economic and asset knowledge connected to a usable workflow, not a separate graph with more nodes.

The Chairman's new information changes implementation responsibility, dependency selection, integration tests and delivery order. It does not invalidate the eight research passes, change the intended depth, authorize weaker evidence, or make a prepared research packet a consumed Fable handoff.

The concrete upstream is no longer just a neighboring proposal. #7780 is the Semiconductor research/design/plan packet. #7870 is its separate implementation carrier and contains a shared assertion schema, its validator, private-root admission classification, rights changes and a Company-owned management-history helper. Its working record reports implementation activity and outstanding private-binding and shared-path questions. The PR is draft and unmerged; this inspection is not independent runtime or production proof. [N01–N05]

The current main evidence schema still has no `curation_assertion` property. Therefore the intended shared capability cannot yet be assumed to exist on the inspected protected product baseline. Mining should prepare against the exact candidate contract while keeping real admission and release gated on accepted shared integration. [N06]

### Three approaches considered

**Selected: shared foundation, Mining-specific consumer.** Reuse native assertion identity, retention/rights, identity resolution, financial/event objects and shared presentation. Add only the domain interpretation, input qualification, source-specific content and tests that Mining requires. Request typed shared changes from the current owner when a requirement does not fit.

**Rejected: fork the Semiconductor implementation.** Copying the schema, publisher, UI or financial history into Mining would reproduce the very identity, correction and privacy problems the shared base is intended to solve. It would also create competing writers on already-owned paths.

**Rejected: wait for every Semiconductor feature before doing any Mining work.** Mining's source selection, schema-fit analysis, examples, native-reader qualification and design can proceed independently. Only an action that actually needs an unavailable or unaccepted component is held. Conversely, speculative tests against a candidate do not authorize live dependency use.

## 3. First release: two different economic tasks on one shared experience

Call this bounded release **Mining M1** in planning prose only. This is not a new runtime enum, canonical theme ID or schema identifier. It is the first useful product slice within the broader Mining mission, not a redefinition of the mission as a two-company product.

### W-C: copper operations and attributable economics

Use the previously researched Freeport/copper case family as the first proposed witness. The reader must identify a supported operating development, distinguish the reporting basis of production and sales, inspect the source-scoped operation/business relationship, and reach a correctly bound issuer economic view. The answer must explain the cash-generation mechanism and a counter-thesis without multiplying an already-attributable input again.

The positive requirement is not an exhaustive valuation of every mine. It is one complete, rights-permitted source-to-operation-to-issuer task using compatible native facts and at least one supported economic comparison. A missing mine-level payable or ownership input blocks its dependent number, not the supported operating fact.

The crosswalk's exact entry is `copper_steel_electrify`, node `theme:copper_steel_electrify`. It has no primary basket and references `reshoring` as a proxy. The Mining research panel therefore needs a theme-level entry through the shared board/panel interface; opening a reshoring basket alone is not acceptance of the copper journey. No dedicated copper basket or `theme:mining` is minted by this design. [N10]

### W-R: rare-earth processing, qualification and retained economics

Use the previously researched MP Materials case family as the contrasting proposed witness under `rare_earth_critical_min`, node `theme:rare_earth_critical_min`, whose crosswalk primary basket is `critical_minerals`. The reader must distinguish material or process-stage output, external sales, intra-group transfers and separately reported contractual income. It must be possible to recognize supported commercial progress without claiming full customer coverage or guaranteed profit.

This tests the same UI and assertion substrate against an integrated processing business rather than hard-coding every company as a single mine selling all production immediately. The financial section must include real owner-admitted economic context and one compatible comparison or reconciliation that is actually supported; a populated map with an empty economics section fails.

The two issuers and source families are proposed acceptance choices, not already-enrolled production objects. At the inspected main pin, Company Intelligence's `production_registry()` contains Apple and four homebuilders, not Freeport or MP Materials. The existing issuer-profile seam provides fact, claim and guidance extractors; its existence does not enroll another issuer automatically. Thus Company-event enrollment for these two witnesses is a concrete source-level gap. This is not a global claim that no Financial Intelligence data exists for either company. [N15–N16]

No current CIK, financial packet, guidance coverage, real private source receipt or owner-valid calculation is fabricated here. A substitute witness requires a written reason showing that it preserves the discriminating economic task, not merely that its data is easier to fetch.

## 4. Exact fit of the shared contract

The inspected contract is a useful foundation, not a universal Mining data model. Its closed shape is a strength: gaps must be addressed explicitly instead of hidden in arbitrary attributes. [N02–N03]

| Mining requirement | Current fit | Proposed treatment |
|---|---|---|
| Source publisher, locator, unknown/date/instant publication, retention and review | Shared fields already exist | Reuse their semantics; a page retrieval date never substitutes for publication or a historical recorded-at receipt. |
| Source-local business/material/equipment/physical-site descriptions | `industrial_context.local_objects` supports closed local kinds | Use only an accurate existing kind. A mine site may be described as a physical facility when that is the source's subject; a reserve model, orebody, ownership interest or contract is not automatically a facility. No global asset identity is inferred. |
| Reported output, shipment, capability or target | Predicates and stage fields exist | Preserve source wording. Commercial stage does not automatically advance when a date passes. |
| Positive physical quantities | `observation.value` supports finite, nonnegative numeric input | Preserve actual unit and basis; do not label every denominator `per_unit` merely to pass validation. A new quantity category requires a shared-owner amendment when existing meanings do not fit. |
| Negative cash, loss or margin | Shared assertion code rejects negative observations; financial packets support signed decimal strings | Route financial values through native financial/event objects. Never take the absolute value, erase the sign, or change to null as a disguise. A financial schema accepting a value is not proof that the metric or issuer is supported by its producer. |
| Ownership percentage versus contractual payable interest | `ownership` exists, but no typed stream/royalty/payability/threshold contract | Allow accurately attributed descriptive evidence. Request one closed shared extension for future computations; do not repurpose `ownership` for a stream. |
| Gross/consolidated/attributable/payable basis | Generic denominator/gross-net text exists; not a complete typed attribution model | Display exact reported basis. Dependent calculations require owner-validated complete semantics; no substring-driven inference. |
| Revision and correction lineage | Native stamps, predecessors and input revisions exist | Reuse. Do not create a Mining correction log or edit prior source meaning in place. |
| Cross-theme use | Refs are scoped using `scope.canonical_theme_id` | Reference the same admitted assertion where the owner permits. Do not remint an identical source claim per research slice to inflate independent support. Changing scope changes content identity and must follow owner semantics. |
| Machine authority | Shared flags are literal false | Preserve every flag and decline any consumer asking research to rank, gate, size, originate or open an entry. |

A sector extension must specify its user gain, exact field meanings, nullable behavior, schema/validator/reader/writer changes, compatibility tests and reviewer. The current shared owner lands that extension once. Mining does not unilaterally change the v1 meaning or hide a breaking change inside an optional field.

The first release deliberately limits automated calculations to accepted native mechanisms. It may provide rich, reviewed explanations of a contract without pretending the prose is a settlement model. Global asset resolution, complete cost curves, real-time supply simulation and automatic contract valuation remain later capabilities with retained research obligations.

## 5. The financial and expectations boundary

The shared `assess_management_sequence(prior, actual, next_outlook, native_derivations=...)` function is a pure Company-owned projection over already-validated inputs. It emits range position, not a general financial calculation engine. It accepts native midpoint receipts rather than calculating a new midpoint itself. [N04]

Its `next_outlook` must refer to a different period from the actual. Mining needs both this sequence and **same-horizon guidance revisions**. A revised full-year mine outlook must not be relabeled as next-quarter guidance to make the function accept it. Same-horizon comparison belongs to the existing Company/financial revision owner; qualify that interface or show the correctly labeled source versions without an unsupported calculated delta.

The helper treats two absent optional bases as equal. That is not proof that two unqualified Mining inputs are economically comparable: its stated precondition is already-validated inputs. Mining intake must establish metric, denominator, currency, period, attribution and perimeter where material before invoking it. A caller cannot launder missing semantics by supplying two nulls. This is a consumer-precondition finding, not a blanket assertion that the shared helper is defective.

Do not force Semiconductor-specific proof requirements onto Mining. M1 requires useful positive issuer economics for both witnesses, but does not demand a fabricated management-outlook triple from a company that does not publish it. Where such history exists and is natively supported, use it. Where it does not, a real financial comparison may satisfy the economic task. Street consensus, management guidance and a Mastermind forecast remain separate.

Financial Intelligence's current entity contract requires a ten-digit CIK and carries separate source-event and system-recorded cutoffs. Foreign/private source businesses lacking a valid supported mapping remain useful industrial evidence; their financial panel must not borrow a parent's identity or fabricate a CIK. [N07–N08]

A security result can be resolved while its issuer axis remains unresolved. Current registrant evidence is not historical ownership lineage. Company navigation, issuer financial joins and asset entitlement are three distinct validations. A positive security link cannot certify the other two. [N08]

## 6. User experience and composition

The reader begins on the existing Themes route. The shared panel presents a Mining research slice within the appropriate existing canonical theme, with explicit coverage. It does not replace the incumbent recommendation, stock-entry, member-order or regional navigation sections.

The first screen should answer in plain language: what changed, which operation or product is affected, why that could matter economically, and the strongest counterargument. Supporting sections provide the relevant physical route, source-attributed business/rights relationships, compatible operating measures, issuer economic context and source access. All views refer to the same selected native revisions.

The physical route is a scoped explanation, not a claim of a globally complete supply chain. A user can follow the material from extraction or purchased feed through conversion to saleable output without mistaking capacity for production or an internal transfer for an external sale. The rights view distinguishes operator, owner, customer and financial claimant rather than encoding all edges as supplier/customer.

For W-C, an attribution boundary should be visible next to the number it qualifies. For W-R, ordinary product sales and a separate contractual-income line must not be visually stacked into one unexplained sales total. Missing contract parameters should appear beside the affected interpretation, not in a generic footer.

The economic panel consumes native financial/event objects. A result may be signed; the UI displays the sign and exact definition. It does not recompute a midpoint, growth rate, attributable quantity, metal equivalent, net asset value or basket weight from rendered strings. Where an accepted native derivation exists, show its result, input references, definition and limitation.

The evidence drawer preserves original source locator, reporting period, revision relationship and current viewing permission. Unknown, disputed, stale, not applicable and unsupported states must remain distinguishable using the accepted native status vocabulary. An unresolved calculation does not delete a known event. A new supported event does not silently refresh an older explanation.

On mobile, the summary and tables remain usable without a large graph. Preserve keyboard navigation, focus return, long labels, English/Chinese presentation and both color themes through the same shared components. Optional graphs must expose coverage limits and must not be the only route to the facts. Do not create a second data transform for translated labels.

## 7. Time, revisions and learning

Preserve at least the source's publication and availability, the source's business-effective interval, the system's observation/retention, the review and the native publication generation. Date-only evidence cannot supply unsupported same-day ordering. A later source correction and a newly issued outlook are different events.

Offer two explicitly different views where supported: reconstructed source history using publications found now, and historical system replay using objects genuinely recorded before the cutoff. Passing a digest check proves bytes, not the time at which Mastermind first knew them. Current identity mappings or revised source pages must not leak into earlier system-cutoff answers.

Revisions append to their existing owners. A changed source marks dependent interpretation for native recomputation or explicit reviewed refresh. If recomputation is unavailable, keep the new observation visible but mark the old interpretation stale. No view may label a new number plus an old incompatible explanation as a coherent updated result.

Cross-domain composition records the selected tuple of native revisions, rights decisions and composition definition. This is a derived transport identity, not another fact database. If an owner changes mid-request, use a still-valid selected tuple or return a section-level stale/refusal state according to the accepted shared contract. Pagination must not splice generations invisibly.

Learning begins with task completion, refused unsupported joins, correction handling and unanswered questions using existing evaluation/analytics owners. Do not log protected payloads. Predictive performance and trade-policy promotion remain outside M1; source-grounded explanation is not evidence of excess returns.

## 8. Privacy and source admission

The schema/validator, a private-root classifier, source rights, product entitlement and production binding are separate controls. `classify_private_evidence_root` accepts declared public roots and required columns from its caller and checks filesystem conditions. Its success does not certify all source rights, publication configuration or live storage custody. [N05]

#7870's recorded R4 question proposes use of the existing Research Vault/private-publication owner. Mining consumes the accepted binding once qualified. It does not settle that shared decision by writing protected assertion bodies into public `data/theme_graph/evidence.parquet`, a new bucket, a static page, or a research artifact. [N01, N06]

Authentication and product entitlement must precede private reads. Current rights apply to current and historical emissions. A revoked source must cease producing prohibited disclosures in a warm process; old licensing snapshots are not permission. Logout and account change must clear private client state, and delayed responses must not repopulate it.

No private bodies or sensitive relationships in public HTML, source maps, browser persistent storage, analytics, logs, counts or distinguishable errors. Source access, permitted retention, user display and redistribution remain separate. Original research documents on #7795 do not grant permission to ingest or redistribute their upstream datasets.

## 9. Delivery sequence and handoff changes

This is design sequencing, not the executable implementation plan or a worker commission.

**M0 — freeze exact consumption boundaries.** Bind the shared contract revision, financial/history interfaces, page mount, rights/private route and accepted dependency-release evidence. Check source writers once on the current carriers; do not infer vacancy from stale chats or empty searches. Record which dependency is still candidate-only.

**M1a — qualify the two witness input sets.** Reuse the eight-pass research to identify exact source spans and native inputs. Establish supported identities, periods, definitions and limits. Create only lawfully scoped synthetic conformance material until private admission is accepted. Unknown issuer enrollment and metric coverage must be resolved rather than hidden behind fixture success.

**M1b — add the Mining consumer.** Use existing owner interfaces and the one shared UI. Add scoped domain mapping and reviewed content, not another storage/identity/correction/publisher implementation. Owner-approved schema deltas land once upstream and are consumed at an exact revision.

**M1c — prove both positive tasks and important failure cases.** Real admitted sources must reach the entitled user and existing company workflow. Prove a source update, an unavailable dependent calculation, current-rights revocation, and unchanged incumbent market outputs. A green schema test or a populated fixture page is insufficient.

**Later — deepen the same product.** Add admitted asset/rights calculations, more families, source coverage and cross-theme queries only where the current owner contracts and evidence support them. The first release is not a global asset census or completion of the whole Mining mission.

The Fable packet must now distinguish three work sets: **reuse**, **Mining-specific implementation**, and **shared-owner requests**. It must identify #7870 as a concrete dependency rather than telling a fresh worker to build a generic sector foundation. Reusable acceptance evidence can be inherited only for the exact unchanged dependency; Mining still needs consumer integration and real-witness proof.

Neither the Mining nor Semiconductor research branch is a product execution workspace. After accepted design/plan and required assignment/custody checks, the designated implementation owner selects the existing lawful implementation carrier or creates one from then-current main only when no incumbent exists. It must not clone #7870 into a competing branch or import unaccepted work merely to avoid a dependency gate.

Fable remains the later orchestrator for cross-owner integration, difficult rights/custody decisions, review adjudication and final delivery. Routine bounded engineering belongs to the least-scarce capable admitted workers. No additional principal, worker, watcher or background execution is created by this design.
