## Scope of this implementation decision

The user's current execution instruction authorizes this bounded continuation.
This is not acceptance of every research recommendation, a reassignment of an
incumbent fact owner, an Executive job, a runtime lease, or native production
admission. Historical owner names identify accountability; their presence alone
does not establish an active worker or require waiting for one.

Fundamental Forensics continues to own its exact retained-source contracts.
Company Intelligence owns this adjacent source-inspection consumer. Data OS
retains identity, temporal and source-policy law. GMI retains semantic and
ThemeState truth. K3-D/Alpha retains propagation composition, and F04 retains
downstream product composition. No second source store, identity allocator,
relationship truth store, graph producer or publishing route is introduced.

## Pure native-reader correction

The canonical receipt dataclass and exception, storage keys, receipt decoder and
bounded decompression implementation move into the existing engine source spine.
The collector re-exports the identical live objects. Receipt JSON bytes, IDs,
keys, size bounds, validation and error behavior remain the persisted contract.
The class/function implementation module changes; the bounded census found no
pickle or module-name consumer, but that is not a cross-version pickle guarantee.

The candidate adapter, native archive reader and attestation manifest-key lookup
use that shared closure. Filing-package materialization remains outside this
repair. The scope does not establish that every Fundamental Forensics operation
is free of acquisition dependencies.

The fresh regression must remain red on the original implementation and on a
manifest-key-only partial repair. A pass requires a fresh child to perform the
actual positive retained read, return the complete expected result, preserve
retained state, and record zero prohibited import or side-effect attempts.
The existing LocalStore constructor boundary remains explicit.

## Bounded review-set consumer

The review set is an explicitly supplied set of candidate/source inputs, with a
unique opaque case ID for every requested item. It extends the existing manual
inspector and CLI. Each usable case calls the real inspector; supplied result
objects cannot substitute for replay. Individual unavailable or malformed files
remain visible case outcomes. Invalid outer requests and aggregate-limit failures
are explicit whole-request refusals with honest processing counters.

The approved engineering limits are 64 cases, 256 KiB per manifest/candidate,
4 MiB per source, 8 MiB aggregate candidate bytes, 64 MiB aggregate source bytes
and 8 MiB serialized output. These limits are resource bounds, not evidence of
economic coverage or measured accuracy. New file-list reads must reject symlink
and nonregular-file hazards through the opened descriptor, without disclosing
host paths or arbitrary exception text.

Reconciliation uses only actual inspectable current views. It may expose exact
duplicate input references, same-candidate-ID payload conflicts and caller-declared
correction/contradiction references. It cannot infer semantic contradictions,
select a winner, erase originals, coalesce legal parties, or reveal excluded
candidate semantics. Repeated source bytes do not become independent evidence.
The content hash identifies the canonical review content; it is not a native
registry attestation, a historical execution receipt or evidence of atomic
filesystem custody.

All per-case and aggregate output remains NOT_ADMITTED with null Graph1 and
false rank, gate, size, trade and prediction authority. Existing single-case API
and valid CLI results retain their behavior. The same native cutoff/profile
rules apply; no invented or borrowed PRODUCED registry row is allowed.

## Acceptance and evidence separation

Synthetic checks establish software behavior. The already retained Micron and
NVIDIA inputs provide separate real-source review evidence, with actual missing
or invalid requests in the denominator. The NVIDIA repaired-reader proof must
keep the historical capture hashes separate from current executing source hashes.
A frozen-candidate replay and an accepted-source replay have distinct receipts.
The two original strict failures remain failed historical observations.

Normal exact-head review, concluded hosted checks, native freshness/baseline
evaluation, expected-head merge and fresh accepted-byte verification are separate
delivery gates. A source report or local test result is not a substitute for
them. A connection timeout records an unknown operation effect until its actual
state is read back; it does not authorize a duplicate write or a new carrier.
