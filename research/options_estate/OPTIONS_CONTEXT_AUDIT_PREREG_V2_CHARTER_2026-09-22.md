## Chosen v2 construction strategy

The implementation child must use bounded streaming with deterministic external-memory canonicalization:

1. **Freeze the source snapshot.** Record source commit/ref, exact path manifest, source device/inode identity where available, byte size, row count, source hash, required append-prefix hash, checkpoint identity for every derivation artifact, freshness clock reading, generation, and the future NYSE session boundary before reading.
2. **Enumerate without sampling.** Enumerate every source path declared by the governed source manifest. For each path, either consume it or emit an explicit contract-backed exclusion. Missing, unexpected, or unclassified owner sources fail closed.
3. **Stream each input once.** Parse JSONL in bounded chunks while computing the full source hash, validating schema, clocks, identity and append-prefix invariants. The scanner must detect shrink, reorder, backdated insertion, in-place mutation, malformed rows, duplicate semantic keys, and source drift between start and end.
4. **Emit bounded sorted runs.** Write content-addressed temporary runs keyed by canonical owner/group key with stable tie-breakers `(available_at, episode_id, source_row)` or the exact schema-defined equivalent. Run metadata includes digest, row count, byte count, ordering identifier, and source generation.
5. **Deterministically merge.** Perform a k-way merge with stable run-digest/path tie-breaking. Reject duplicate semantic owners with conflicting payloads. Validate one-to-one source/reference counts and exact legacy/v2 owner joins during the merge.
6. **Stream the final set.** Emit canonical reference bytes in the frozen owner order, compute the complete reference-set hash, and write the receipt only after all validation passes. Publish the receipt atomically; no partial receipt or health claim is valid.

Canonicalization semantics, stated precisely (review finding 4 repair, part 1): the canonical owner order, the canonical reference bytes, the reference-set hash, and the canonical count depend only on the **ordered source snapshot plus the frozen semantic contract** — the declared schema, validators, tie-breakers, and cohort/classification rules. They do not depend on chunk size, run partition, iteration order of in-memory hash maps, or any other incidental computation detail. An implementation in which a change of in-memory map iteration order changes canonical output is non-deterministic and refuses with `NONDETERMINISTIC_OUTPUT`. A change in the ordered source bytes — reorder, prefix change, mutation, shrink — is not a reproducibility difference at all; it refuses under the source-integrity rules. These two cases must never be conflated: one is a determinism defect, the other is a different (or tampered) input.

If a source is proven append-ordered by a checked invariant, a one-pass fast path may avoid external sorting. The same invariant must be verified on every run; otherwise the implementation must use the external merge path or refuse. The fast path is an optimization, not a separate authority.

The strategy costs O(N) input and output I/O and O(N log N) comparisons in the external-sort path. Peak memory is bounded by the configured run chunk. Temporary disk is bounded by the run manifest and high-water limit. No row, owner, correction, or source may be evicted to satisfy those limits. **Incremental generations are additionally constrained by the full-generation rule** stated later in this charter; a suffix-only HEAD is forbidden in all cases.

## v2 receipt and schema contract

The new v2 schema, builder, and receipt are a new preregistration triad. v1 remains byte-frozen, independent, and the sole selected authority until the transition in "Succession and registration". Two independently hashed objects separate semantic identity from attempt evidence. An outer publication envelope binds both digests; it is not part of the semantic object. This separation repairs review finding 4 without a circular or attempt-dependent semantic hash.

**Semantic section — byte-identical across replays.** Every field determined by the ordered source snapshot plus the frozen semantic contract:

- schema and preregistration version;
- operation ID and immutable source commit/ref;
- the NYSE session boundary and freshness policy actually in force (frozen per "Corrections, replay, retry, and session boundary");
- complete source manifest, including consumed and explicitly excluded artifacts, with per-artifact path, digest, byte count, record count, generation, checkpoint identity, and prefix digest where required;
- canonical owner/reference ordering identifier;
- algorithm identifier and source parser/validator contract digests;
- correction/replay lineage (`supersedes`, old/new source hashes, and generation IDs);
- reference-set digest and canonical count;
- per-source counts of rows accepted as prospective, classified retrospective, abstained, or refused, broken down by reason code, with nulls printed rather than implied;
- typed refusal code when no receipt is emitted.

The semantic object contains no attempt identity, elapsed time, attempt-evidence digest, envelope digest or incidental run partition. Hashes flow in one direction: canonical semantic bytes → semantic digest; separately serialized attempt bytes → attempt digest; outer envelope → both digests. Replay compares semantic bytes/digest only. The envelope and attempt digest may differ between separately admitted verification attempts; neither variation permits another publication for an already committed operation.

**Attempt-evidence section — bound by digest, not required to be byte-identical.** Every field that describes how one attempt of the work was actually executed. This is immutable evidence of that attempt, written once and never rewritten; the outer envelope binds its digest beside the semantic digest, but two replays of the same operation are not required to agree on it:

- run manifest with run digests, run count, rows and bytes per run, partition and ordering identifiers;
- temporary-disk high-water and staging-space floor observed;
- observed peak process RSS and **cgroup memory peak** (see "Service envelope and staging policy");
- CPU seconds, wall seconds, input/output bytes, and wall-clock timestamps of the attempt;
- byte counts of already finalized audit and reference-set objects.

Envelope and HEAD lengths/hashes are recorded by the incumbent post-write journal/readback, outside those objects. No object includes its own serialized length/hash or a digest of an object that hashes it. The later schema must preserve this acyclic order and test it; the charter does not claim a finalized builder.

A replay whose **semantic section** differs in any field from the original publication is `REPLAY_MISMATCH`. A replay whose semantic section matches and whose attempt-evidence section differs is semantically reproducible verification under different runtime conditions — not a mismatch and not permission to repeat a publication effect. Determinism is judged on semantics; attempt evidence is judged only on internal consistency and reconciliation (counts and digests must reconcile with what was written, even when timings differ).

The forward-cohort rule resets at the boundary frozen in "Corrections, replay, retry, and session boundary". Rows before that boundary are retrospective or abstain according to the frozen contract; delayed observation cannot make them prospective. A rule, source, validator, or schema change requires a new version and a new forward cohort under the succession rule; nothing in this charter changes a cohort by acceptance alone.

## Corrections, replay, retry, and session boundary

**Correction and lineage.** A successful receipt is immutable. A correction that changes already committed source bytes creates a new generation with an explicit `supersedes` link and exact old/new hashes; it never overwrites the old receipt, and it never rewrites the old source's recorded bytes or digests — the old generation keeps its historical identity even where the live ledger now carries corrected rows. The **correction row format** (how a correcting writer appends a revision, and which fields carry the supersedes pointer) is a preregistration field: the implementation child must define it in the semantic contract before implementation, and acceptance test 5 cannot pass without it. A backdated insertion, source shrink, reorder, prefix mismatch, conflicting duplicate, or source mutation during a scan discards uncommitted runs and returns a typed refusal.

**Retry, exactly-once, and crash recovery (review finding 4 repair, part 2).** Before performing any exactly-once effect — publishing the reference-set or audit objects, or committing the receipt HEAD — a retry of an operation ID must **first inspect the durable evidence of the original attempt**: the journal and the object store. Three cases, each with a required outcome:

1. **Fully published** (HEAD present for that operation ID): the retry must not recompute and republish. It reads back the published receipt, verifies its semantic section against that published operation's frozen manifest and source snapshot; a later append belongs to a new generation, not a mismatch against the committed original, records the reconciliation in the journal, and exits without a second HEAD. It must not require the original attempt's timings or run partition to be reproduced, and a failure to reproduce them is not `REPLAY_MISMATCH`.
2. **Partial or uncertain publication** (objects observed, HEAD absent or acknowledgement lost): absence in one read is not proof of non-application. Preserve original objects, journal, operation and pending writer; do not delete, overwrite, recompute-and-republish or launch a replacement while any original effect is UNKNOWN. Reconcile through the original publication protocol using authoritative object/version/conditional-write evidence and acknowledged writer settlement or enforceable exclusion. Only a proven settled operation may enter its separately specified recovery path. That path must preserve original immutable evidence and either finish the already-claimed original commit under its exact conditional protocol or return the stable operational state `EFFECT_UNKNOWN` outside the scientific receipt/refusal vocabulary. That state authorizes neither deletion nor another publication. This charter grants neither retry nor cleanup authority.
3. **Proven never published**: ordinary computation is eligible only when original dispatch absence or authoritative original-attempt settlement establishes no outstanding write; a missing HEAD alone is insufficient.

Blind replay — recomputing and republishing without the journal/object inspection — is forbidden in all cases. A changed source or changed operation/session identity is a new generation, not a retry of the old effect. Acceptance test 9 enumerates the crash-before-commit and crash-after-commit cases explicitly; revision 1 named "interrupted writes" in prose only.

**Freshness, staleness, and the boundary clock (review finding 11 repair).** The following integrity rules are fixed; the missing age/clock parameters are explicit preregistration prerequisites, not invented measurements:

- **Freshness clock:** the freshness reference is the completion instant of the bound source generation, recorded in the manifest and in the accepted registration. Every artifact's identity in the manifest is its digest, row count, byte count, and (where applicable) required append-prefix digest and checkpoint identity at that instant.
- **Integrity and derivation checks:** source bytes differing from the bound manifest refuse with the existing mutation/prefix code. A derivation checkpoint missing or differing from the bound owner prefix refuses `CHECKPOINT_STALE`. Neither is a substitute for measuring source age.
- **Open age/clock contract:** before implementation admission, registration must freeze the trusted scan clock, each source's event/availability clock, timezone and session-calendar rules, the allowed nonnegative age and future-skew bounds, missing-clock treatment and boundary comparison. It must separately test too-old and future-dated rows without silently rebinding the generation. No numeric threshold or current freshness is established here; absent this contract, freshness qualification is unavailable.
- **Stale-source policy:** any stale condition refuses; the audit never silently re-binds a new generation while presenting itself as the same run, and never treats staleness as a warning.
- **Session boundary:** the boundary is the first NYSE session open after the latest of (i) the `registered_at` instant of the accepted v2 registration and (ii) the first protected-`main` commit containing the exact required digests named in "Succession and registration", and (iii) the acknowledged qualified installation/selection instant described there. The v1 selector rule remains unchanged. This proposed v2 extension additionally prevents retroactive prospective treatment of rows predating actual qualified selection. Acceptance, registration and merge alone do not activate v2. No row may be backdated into that cohort.

**Cross-file snapshot.** A cross-file snapshot is mandatory. Stable-read checks on individual files are insufficient: the implementation must bind one source generation/checkpoint across episodes, outcomes, campaign ledgers, campaign outcomes, checkpoint artifacts, and canary/config inputs, then refuse if any file or checkpoint moves between reads. This requirement is acceptance test 10, numbered rather than prose-only.

**Incremental generations — the full-generation rule (review finding 8 repair).** Incremental mode may reuse only **authenticated prior generation evidence**: a prior generation whose receipt chain, prefix digests, and manifest identities verify against the current bound snapshot. Under that mode an incremental run re-reads and re-hashes the appended suffix and re-authenticates the prior prefix chain, and the HEAD it publishes — every HEAD, in every mode — contains the **complete reference set over the full owner population**, never a suffix-only or newest-window subset. If prior evidence cannot be authenticated, the run falls back to a full scan; if the full scan cannot complete inside the envelope, the run refuses with a typed refusal. A suffix-only HEAD resolves older owners as absent and is owner eviction by construction, forbidden by `DNR:KILL-OPTIONS-CONTEXT-AUDIT-OWNER-EVICTION`.

## Resource envelope, benchmark prerequisite, and refusal contract

**The benchmark is a precondition, and no numeric limit is chosen here.** The implementation child must benchmark the corpus it binds (the 2026-10-11 refresh above, or a newer re-measurement at its own source head taken per the provenance rules in "Capacity refresh") and the candidate fixture scale, **before freezing numeric limits**. The benchmark must run **under the actual service class** — the real audit unit on a test host, or `systemd-run` with the identical properties — at both the bound corpus and the fixture scale, and must measure at least:

- input rows and bytes per source;
- JSON parse and validation CPU seconds;
- reference construction CPU seconds;
- context-store resolution cost, which revision 1's disposable prototype omitted and which is the per-episode stage of the incumbent auditor;
- sorting/merge CPU seconds and run count;
- peak process RSS **and** cgroup memory peak with `MemoryHigh`/`MemoryMax` event counts (see next section);
- temporary-disk high-water and available-space floor;
- canonical reference-set bytes, audit bytes, receipt bytes and HEAD bytes;

**Feasibility is not claimed here (review finding 6).** The dated evidence cuts against comfort, not toward it: v1 spent 90.134 CPU-seconds at 3,897 rows on 2026-08-22 and did not finish (`DSC:OPTIONS-CONTEXT-AUDIT-V1-TIMEOUT-PRECEDES-4096-REFUSAL`); the disposable prototype peaked at 274,907,136 bytes (about 262 MiB, macOS `ru_maxrss`) on the design-SHA corpus, already above `MemoryHigh=256M`, and measured neither context-store resolution nor final receipt serialization nor any campaign-v2 input. Inside a 50% CPU quota, 150 wall seconds is at most about 75 CPU-seconds of budget. This charter does not assert that the complete-population workload fits that envelope; it does not assert that it does not. **Open prerequisite:** the benchmark receipt decides it. If the measured complete-population workload exceeds the envelope at the bound corpus or at the fixture, the honest outcomes are: the implementation is not accepted within this service class and the record says so, or a separately admitted service-change preregistration is proposed and reviewed on its own merits, or v2 stands as a fail-closed audit that receipts `RESOURCE_LIMIT` on real input — each of those is a stated outcome; none of them is silent widening, and none of them may be executed by this charter, by a seat decision, or by the implementation child on its own authority.

Limits, once benchmarked, must include measured headroom and separate row and byte ceilings for episodes and h60. The incumbent eight-megabyte h60 capture cap cannot be reused as a v2 sizing input because the h60 artifact already exceeded it in the 2026-10-11 refresh (about 48.5 MiB); it stays live and pinned for v1 regardless. Numeric limits are implementation acceptance inputs, chosen from the benchmark receipt and judged under the changed-risk review; they are not chosen in this charter.

The implementation must fail closed, emit no receipt, and leave no accepted health claim on:

- incomplete or unclassified owner population;
- missing, malformed, stale, mutated, reordered, shrunk, or hash-mismatched source;
- legacy/v2 campaign contract mismatch;
- duplicate semantic owner or conflicting duplicate;
- source/reference count mismatch;
- nondeterministic run or merge output;
- context-generation or source-prefix drift;
- correction without a new generation;
- RSS, cgroup memory, CPU, wall-time, input-byte, output-byte, or temporary-disk limit breach;
- receipt/reference-set/HEAD size overflow;
- replay whose semantic section differs from the original publication.

Refusal codes must be machine-readable, stable, and included in the implementation acceptance tests. Failures must not be swallowed, windowed, sampled, truncated, evicted, or converted into a healthy empty result. The refusal vocabulary is frozen exactly as revision 1 froze it: `SOURCE_MANIFEST_INCOMPLETE`, `SOURCE_SNAPSHOT_UNSTABLE`, `SOURCE_MUTATED`, `MALFORMED_ROW`, `PREFIX_MISMATCH`, `CHECKPOINT_STALE`, `CAMPAIGN_OUTPUT_STALE`, `DERIVATION_PENDING`, `CAMPAIGN_REPLAY_MISMATCH`, `OWNER_MISSING`, `DUPLICATE_OWNER_CONFLICT`, `CORRECTION_LINEAGE_MISSING`, `DEPENDENCY_MISMATCH`, `BOUNDARY_INVALID`, `NONDETERMINISTIC_OUTPUT`, `REPLAY_MISMATCH`, `RESOURCE_LIMIT`, `RECEIPT_OVERFLOW`, and `AUTHORITY_VIOLATION`. No code is added or removed by this revision. Each refusal records the operation ID, source-generation ID, per-source digests/counts, checkpoint IDs, and the first failing stage.

**Refusal before kill: the service envelope is fixed, and the ordering is a tested property**

`app/deploy/macro-market-memory-options-context-audit.service` carries `TimeoutStartSec=180`, `CPUQuota=50%`, `MemoryHigh=256M`, `MemoryMax=512M`, `Nice=10`, `CPUWeight=20`, and `IOWeight=20`; v2 raises none of them. `DSC:OPTIONS-CONTEXT-AUDIT-V1-TIMEOUT-PRECEDES-4096-REFUSAL` records the dated design rationale: an O(N) construction killed by the timeout leaves no receipt and no refusal code, indistinguishable from a run that never started. v2's contract requirement is to invert that ordering — this is a contract the implementation must demonstrate, not a property anyone has measured for v2:

1. **In-process limits fire first.** Every resource limit is enforced inside the process and trips before its systemd counterpart: wall budget at most 150 seconds (a 30-second margin under `TimeoutStartSec=180` to serialize the refusal record); CPU budgeting that treats `CPUQuota=50%` as halving available CPU (a stage measured at T unthrottled CPU-seconds costs about 2T wall-seconds); a memory budget set below `MemoryHigh=256M` on the accounting basis of the next section.
2. **Checked where the work is.** Budgets are checked at every stage boundary and at bounded intervals inside each parse, run-emit, and merge loop, so an over-budget input ends in `RESOURCE_LIMIT` with the first failing stage recorded — not in a timeout, a throttle stall, or an OOM kill.
3. **Acceptance.** An over-envelope fixture run under the real service class yields a `RESOURCE_LIMIT` refusal record and an exit status distinct from success; the journal shows no SIGKILL, timeout, or OOM event, verified against cgroup event counters and the unit journal together.

Whether a correct, complete-population run can finish inside that envelope is precisely the open benchmark prerequisite above; this section requires that *failure* be observable, and claims nothing about the feasibility of *success*.

## Service envelope and staging policy (review finding 15 repair)

The unit's sandbox is part of the fixed envelope. `PrivateTmp` is on, `ProtectSystem=strict` is on, and the unit exposes a single `ReadWritePaths` directory. The external-sort runs of "Chosen v2 construction strategy" are written **inside that sole writable path**, under a per-operation subdirectory named by the operation ID, created and cleaned up by the audit process itself:

- No new writable path, no `ProtectSystem` relaxation, no `PrivateTmp` escape, no privileged helper, and no capability grant is authorized, requested, or implied by this charter. If the sole writable path lacks space for the run manifest plus its floor, the run refuses `RESOURCE_LIMIT` with the staging high-water recorded; it never writes elsewhere.
- The staging policy is: runs are content-addressed. Cleanup may remove only proven local temporary files after original writer/effect settlement under the existing cleanup protocol; immutable published evidence and any uncertain operation are retained. Starting an operation never itself grants a sweep or retry, and the receipt's attempt-evidence section records the staging high-water and the free-space floor observed.
- **Memory accounting basis.** Process RSS is not the quantity `MemoryHigh` and `MemoryMax` throttle and kill on; the cgroup's memory accounting includes page cache and other charges the process does not see in `ru_maxrss`. The in-process memory budget is therefore enforced against the cgroup's own accounting (read from the cgroup's memory files where available inside the sandbox, not from process RSS alone), and the acceptance check for "no throttle, no OOM" reads the cgroup's `MemoryHigh`/`MemoryMax` event counters, not RSS. Whether a streaming implementation can hold under `MemoryHigh` on this corpus is part of the open benchmark prerequisite; this charter asserts no cgroup feasibility.
