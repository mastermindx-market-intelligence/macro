## 5. One best executable next slice: frozen review-set inspection

### User capability

An analyst can submit one frozen list of explicitly chosen candidate/source inputs and receive one bounded review result answering: which requested observations replayed; which were refused, missing or not yet knowable; which candidate/revision references conflict or remain unresolved; and which source inputs each result used. It removes repeated manual one-file runs and creates a reproducible input denominator for the planned diagnostic cohort.

It does not answer whether the world contains no other relationships. It does not estimate admission precision, establish issuer coverage, declare a winner among contradictory assertions or publish a graph.

### Smallest implementation

Extend the **existing** `engine/company_intelligence/relationship_candidates.py` with a pure review-set function that delegates every case to the existing `inspect_candidate`. Extend its existing `main` with a mutually exclusive review-set file mode; preserve the one-candidate CLI output and exit semantics exactly. Reuse the current bounded file/JSON parsing rather than adding a generic filesystem crawler, source registry or processing service. Add a dedicated focused review-set test file and enroll it through the existing `company-relationship-candidates` CI job, with closure measured against the actual imports. Do not create a second exclusive job or raise packing ceilings.

The proposed interface is a source-only extension, not an installed contract yet. The principal should freeze exact names/version and limits in the implementation. A reasonable initial envelope is no more than 64 requested cases, the existing 4 MiB source and 256 KiB candidate per-file limits, plus an explicit total source-byte and total output budget. Counts and byte limits are engineering bounds, not empirical findings.

Inputs should contain an opaque unique review case ID, explicit candidate input and explicit source binding. Native-source callers may use the separately repaired pinned API, but this first CLI increment must not construct a `LocalStore`, discover manifests or introduce a fetcher merely to imitate a production reader. An output JSON supplied by a caller is not a substitute for replaying the actual source input.

### Required output behavior

1. Preserve one disposition for every requested case. A bad source or candidate is an explicit refused/unavailable case, never silently removed from a success denominator. A malformed outer envelope receives a typed whole-request refusal.
2. Retain each successful inspector result and every original refusal code without widening admission. The aggregate must state `NOT_ADMITTED`, null graph/predictive outputs and false authority, just as its inputs do.
3. Report **input-processing denominators**: requested cases, unique supplied source digests, inspectable cases, refused/unavailable cases and not-known-as-of cases. Label these counts by their exact meaning. Do not call them true relationships, issuer universe coverage, source recall or precision.
4. Preserve candidate/revision identity and report same-ID/different-payload collisions, supersession references to absent cases and contradiction references. Do not choose a current winner, erase originals, equate duplicate sources with independent corroboration, or infer semantic contradictions from similar prose.
5. Load the caller-supplied native registry once and apply the same exact cutoff to each item. A missing relationship dataset remains a native eligibility refusal. Do not add an ephemeral handcrafted `PRODUCED` row to make the batch historically inspectable.
6. Derive result identities from the frozen input list and verified byte identities; wall time must not change semantic digests. Keep missing input/status distinct from an explicitly empty review set. If empty sets are disallowed, return that refusal rather than a misleading complete-zero result.
7. Omit dedicated source support by default, retain the existing manual-annotation content caveat, and perform no public upload or rights reinterpretation. No absolute host paths or raw exception/source text in refusal diagnostics.

## 6. Production native adoption that this does not replace

The production path can proceed without waiting for a historical person's availability, but it needs an explicit accountable integration decision and actual implementation. The minimum decisions are concrete:

- **Observation species and scope:** choose one native fact first, such as a source-observed named supplier-roster membership or a planned product integration. Do not begin with an all-purpose `SUPPLIES` fact. Specify legal-party versus source-local identity, source occurrence, exact revision and contradiction semantics.
- **Producer and native row:** bind the observation to the existing retained filing reader and real immutable receipt; implement a producer in the existing specialist/Company Intelligence ownership. Choose the Data OS temporal profile from its actual natural clocks and correction grain. Register `PROPOSED` until a real producer/store exists; obtain authentic historical observations before promoting replay eligibility.
- **Source-purpose policy:** implement the exact existing-owner rule for internal analysis, retained excerpts, serving and any export. Separate use-specific grants. A filing's public location and a native hash cannot authorize model training or redistribution.
- **Identity:** consume exact current identity where applicable, preserve historical and subsidiary ambiguity, and keep issuer-document ownership separate from each asserted relationship party. No auto-resolution of pronouns or commercial aliases.
- **Incumbent consumer:** select one exact accepted downstream interface in Company Intelligence/F04/private publication; bind a versioned positive case and a refusal case. If that interface is still on a held carrier, integrate through its existing lane once accepted rather than copying it.
- **Production proof:** real retained source -> actual native observation -> correction/refusal-aware served consumer under the right purpose/entitlement. Source code, a manual registry row, a local fixture and a green test suite do not individually prove this chain.

The ready review-set extension is useful while these contracts are made concrete. It should not be represented as the admitted-fact milestone, and no proposed batch code is authorized by this worker report alone; the principal remains the source execution and release owner.
