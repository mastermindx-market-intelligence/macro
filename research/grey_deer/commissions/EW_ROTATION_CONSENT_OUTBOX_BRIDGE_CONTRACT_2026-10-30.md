## Proposed minimal trustworthy activation fence — independent approval required

**Problem:** The Auth user_metadata merge-write race means current `alert_email_optin` alone cannot prove latest effective revocation. The producer also lacks a trusted timestamp for when each user truly began receiving this alert family. Treat both as explicit release blockers; a new per-user bridge cannot be safely default-enabled until the preference authority and delivery owner approve a durable atomic solution.

**Preferred option for owner adjudication:** Extend the **existing** `public.email_prefs` preference row (not a new state plane) with a narrowly scoped rotation-family activation/safety fence, e.g. reviewed `rotation_observation_enabled` (default false), `rotation_observation_activation_at` (server timestamp), and `rotation_observation_revision` (monotone integer). A single authenticated, server-owned transaction/RPC or equivalent reviewed atomic UPDATE changes those related fields together; unrelated language/theme/brain-depth paths do not write them. This is a safety receipt, not a duplicate general preferences store. If migration of alert consent into the existing preference row would violate the owning privacy/versioning architecture, return the **different exact approved existing atomic owner**; do not implement the candidate columns by fiat. A versionless Get-then-Put mirror in another document does not solve the race.

**Fail-closed effective permission at every gate:**
```text
effective_rotation_permission :=
    authenticated_and_entitled_user
    AND current_auth.user_metadata.alert_email_optin == true
    AND "sector_rotation_relative" in trusted selected categories
    AND existing suppression / quiet hours permit
    AND server-owned rotation_activation.enabled == true
    AND source receipt is eligible, lawfully timed, rights-authorized and not withdrawn
    AND receipt.observed_at >= server_owned_activation_at
    AND current_activation_revision == row.activation_revision
```
If any authorization read is missing, future-dated, incorrectly typed, mismatched or unavailable, result is `UNAVAILABLE/PENDING` or suppression according to existing typed drain contract, **never deliver** and never interpret as no users. Do not use the source's retrospective market `source_as_of` as the delivery availability/opt-in clock.

**Opt-out ordering:** persist the server-owned rotation fence `enabled=false` FIRST, confirm readback, then apply legacy Auth metadata update if that surface remains; if subsequent Auth write fails, keep enabled=false and surface partial-save, not success. A delayed unrelated language metadata PUT cannot re-enable the fence. Enabling requires explicit user action, successful normal metadata write, then activation fence server transaction and readback. Failed half-activation leaves the fence false. Every fresh enable/reset increments revision and establishes a *new* non-backfill boundary. The UI must not assert success from the unrelated email language mirror.

**Subscriber→outbox binding:** complete roster pagination through the existing auth/preferences owner (authenticated service, identity verification, entitlements, bounded failures). Snapshot a canonical immutable observation ID/prev ID/revision and eligibility. For each still-opted-in user whose **activation was before the immutable observed time**, derive deterministic unique logical `fire_event_id` from existing canonical event/observation identity + user identity + category + declared schema version (no arbitrary retry nonce) and insert into the **existing** `public.alert_outbox`. Unique conflict ≠ sent: read back identical or divergent identity; unknown POST effect remains uncertain until exact canonical target reconciliation. Catchup of missed same-active-event allowed only if source hasn't expired and recipient was already active at observation, not on newly subscribed user. Corrections/withdrawals carry linked fresh receipt, not silent edit to an already-sent row.

**Drain, send and supersession:** a receipt queued at activation revision 12 is not eligible after opt-out/re-opt-in at revision 13 even if Auth metadata erroneously still says true. Re-read the trusted fence at final *pre-transport* admit and before calling mailer; stale permission, expired source, withdrawal, and known superseded item suppress the logical row. Already claimed/SMPP-in-flight or final-DATA-unknown send cannot be retrospectively cancelled; leave `effect_unknown` quarantine and issue a distinct sourced correction when appropriate. Claim only best available at-most-once semantics. **Do not** invent a new PostgREST `status` enum, and do not send a withdrawal without checking whether initial alert was actually delivered or its effect uncertain.

**Compatibility option (not a substitute):** A narrower Auth metadata patch instead of full merged JSON may reduce lost updates, but unless its upstream Auth implementation is proven to serialize concurrent writes, it is not an atomic consent guarantee and cannot release the fence.

## Independent-review disposition: revocation linearization and correction ancestry (2026-10-30)

**Source of challenge:** independent architecture [#10219 review comment 6535221836](https://github.com/mastermindx-market-intelligence/macro/pull/10219#issuecomment-6535221836), B4/B5. This is a **candidate contract amendment, not approved DDL, code, recipient authorization, source reclassification or independent security review**. The preceding example activation fields are illustrative, not a final schema owner decision.

### A. Permission ownership and version serialization

An explicit global alert-email opt-out, removal of `sector_rotation_relative` from selected categories, and rotation-family opt-out all MUST revoke the one effective rotation-sending right before the UI acknowledges success; protecting only `rotation_observation_enabled` is insufficient. Put that authority behind the **existing Auth/preferences owner's** reviewed server-owned atomic route/fence. Every relevant setting transition carries server-issued **expected revision/CAS** or equivalent serial lock, checked against the *actual* immediately preceding revision, not merely a new monotonically incremented integer. A stale enable submitted after an acknowledged disable is rejected as a conflict, not silently applied.

Do not leave a conflicting old metadata path able to overwrite that effective right by delaying a language/theme PUT or restoring a previous global/category selection. If compatibility reads must include old `user_metadata`, they may **further restrict** permission but must never override a newer server-owned revocation. Existing `email_prefs.marketing_opt_out` is marketing-specific and not a proxy for this authorization. Fail the UI with partial-save/conflict on any mismatch; a generic `ok=true` language mirror cannot signal consent.

**Hard no-send admission** requires simultaneous verification of auth user, tenant, entitlement, current revocation revision, current global/category/family effective permission, original event activation ancestry, native observation availability/rights, legal expiry, suppression and quiet hours. Missing data, stale roster page or permission read returns typed unavailable/no-send; a permissive default is prohibited.

### B. Explicit send-admission linearization

A `SELECT` or GET followed by SMTP is **not** an atomic proof against the concurrent revocation race `read(true) → disable → send`. The existing outbox/drain and preference authority must agree on a **single serialized pre-transport admission action**, using their existing tables/transaction owner rather than adding a second queue or permission store. The action revalidates effective permission, activation revision, observation lineage, expiry, target user and same logical `fire_event_id`, and marks the existing row admitted (or refused) under a lock/CAS that is ordered with revocation. **Revocation's acknowledged transaction and send admission must have one defined order.** After revocation commits, no *new* admission is allowed. A transport already admitted before revocation may complete; do not claim retroactive SMTP cancellation.

This design still requires owner adjudication for the existing drain's claim/status workflow; it does not authorize inventing a database enum, holding a DB transaction across SMTP, another status plane or a second drain. Accepted SMTP DATA followed by connection loss remains `effect_unknown`; never emit a new nonce/row to disguise uncertain acceptance, and never mark as delivered without a trusted delivery receipt.

### C. Immutable observation and correction eligibility

The immutable **original observation** determines whether a subscriber could legitimately receive its correction or withdrawal: retain the originally issued observation ID/observed_at/activation epoch, original subscriber entitlement and delivery state, then link corrections with their own later issuance/source revision. **A correction timestamp cannot make a pre-opt-in observation retroactively eligible** or extend the source beyond expiry. A fresh same-event correction or withdrawal is not a newly eligible baseline for late opt-ins. Before sending a withdrawal to a user, confirm whether the original was delivered, was never queued, or remains SMTP effect-unknown; uncertain status requires owner-defined quarantine/corrective messaging, not a fabricated delivery.

### D. Owner-owned negative tests and release proof

- Two signed-in tabs: older enable request arrives after acknowledged global or category disable; expected revision mismatch, no successful re-enable, **zero newly admitted mail**.
- Unrelated delayed language metadata writes stale `alert_email_optin=true` after opt-out, and subsequent enqueue/claim/drain re-read; never send.
- Adversarial `drain reads true → revocation commits → SMTP invoke`: no new admission after revocation. The converse `admission committed → revocation commits → in-flight SMTP accepted` is recorded as admitted-before-revocation, not false revocation failure.
- Stale/partial category roster, absent `email_prefs`, unavailable Auth admin, missing entitlement, rights not proven, expired source or a retracted observation: no-send with typed reason and no "zero subscribers success".
- New opt-in after original event followed by a correction/withdrawal for that event: **no backfill**. Two revisions of same permitted event do not create two logical send identities for same meaning; actual correction to earlier delivered user has linked provenance.
- SMTP accepted/connection drops after DATA: existing effect-unknown quarantine only; no duplicate transport under synthetic retry, re-run or new generated UUID.
- Existing user prefs account UI EN/ZH and signed-in product receipt must show effective permission and canonical event identity. No source write, email, migration, production claim or safety release based solely on these proposed tests.
