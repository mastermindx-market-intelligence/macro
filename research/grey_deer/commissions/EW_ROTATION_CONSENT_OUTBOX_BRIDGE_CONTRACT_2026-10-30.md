## Proposed minimal trustworthy activation fence — independent approval required

**Problem:** The Auth user_metadata merge-write race means current `alert_email_optin` alone cannot prove latest effective revocation. The producer also lacks a trusted timestamp for when each user truly began receiving this alert family. Treat both as explicit release blockers; a new per-user bridge cannot be safely default-enabled until the preference authority and delivery owner approve a durable atomic solution.

**Preferred option for owner adjudication:** Extend the **existing** `public.email_prefs` preference row (not a new state plane) with a narrowly scoped rotation-family activation/safety fence, e.g. reviewed `rotation_observation_enabled` (default false), `rotation_observation_activation_at` (server timestamp), and `rotation_observation_revision` (monotone integer). A single authenticated, server-owned transaction/RPC or equivalent reviewed atomic UPDATE changes those related fields together; unrelated language/theme/brain-depth paths do not write them. This is a safety receipt, not a duplicate general preferences store. If migration of alert consent into the existing preference row would violate the owning privacy/versioning architecture, return the **different exact approved existing atomic owner**; do not implement the candidate columns by fiat. A versionless Get-then-Put mirror in another document does not solve the race.

**Fail-closed effective permission at every gate:**
```text
effective_rotation_permission :=
    authenticated_and_entitled_user
    AND current_auth.user_metadata.alert_email_optin == true
    AND "sector_rotation_relative" in trusted selected categories
    AND existing suppression / quiet hours permit
    AND server-owned rotation_activation.enabled == true
    AND source receipt is eligible, lawfully timed, rights-authorized and not withdrawn
    AND receipt.observed_at >= server_owned_activation_at
    AND current_activation_revision == row.activation_revision
```
If any authorization read is missing, future-dated, incorrectly typed, mismatched or unavailable, result is `UNAVAILABLE/PENDING` or suppression according to existing typed drain contract, **never deliver** and never interpret as no users. Do not use the source's retrospective market `source_as_of` as the delivery availability/opt-in clock.

**Opt-out ordering:** persist the server-owned rotation fence `enabled=false` FIRST, confirm readback, then apply legacy Auth metadata update if that surface remains; if subsequent Auth write fails, keep enabled=false and surface partial-save, not success. A delayed unrelated language metadata PUT cannot re-enable the fence. Enabling requires explicit user action, successful normal metadata write, then activation fence server transaction and readback. Failed half-activation leaves the fence false. Every fresh enable/reset increments revision and establishes a *new* non-backfill boundary. The UI must not assert success from the unrelated email language mirror.

**Subscriber→outbox binding:** complete roster pagination through the existing auth/preferences owner (authenticated service, identity verification, entitlements, bounded failures). Snapshot a canonical immutable observation ID/prev ID/revision and eligibility. For each still-opted-in user whose **activation was before the immutable observed time**, derive deterministic unique logical `fire_event_id` from existing canonical event/observation identity + user identity + category + declared schema version (no arbitrary retry nonce) and insert into the **existing** `public.alert_outbox`. Unique conflict ≠ sent: read back identical or divergent identity; unknown POST effect remains uncertain until exact canonical target reconciliation. Catchup of missed same-active-event allowed only if source hasn't expired and recipient was already active at observation, not on newly subscribed user. Corrections/withdrawals carry linked fresh receipt, not silent edit to an already-sent row.

**Drain, send and supersession:** a receipt queued at activation revision 12 is not eligible after opt-out/re-opt-in at revision 13 even if Auth metadata erroneously still says true. Re-read the trusted fence at final *pre-transport* admit and before calling mailer; stale permission, expired source, withdrawal, and known superseded item suppress the logical row. Already claimed/SMPP-in-flight or final-DATA-unknown send cannot be retrospectively cancelled; leave `effect_unknown` quarantine and issue a distinct sourced correction when appropriate. Claim only best available at-most-once semantics. **Do not** invent a new PostgREST `status` enum, and do not send a withdrawal without checking whether initial alert was actually delivered or its effect uncertain.

**Compatibility option (not a substitute):** A narrower Auth metadata patch instead of full merged JSON may reduce lost updates, but unless its upstream Auth implementation is proven to serialize concurrent writes, it is not an atomic consent guarantee and cannot release the fence.
