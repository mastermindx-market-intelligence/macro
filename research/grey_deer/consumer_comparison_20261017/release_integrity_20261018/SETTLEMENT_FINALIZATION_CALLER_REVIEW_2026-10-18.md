## Conditional contract gaps and retry limits

**Migration-link success is treated differently.** For an autonomous receipt with a submission, `persist_settlement_link(receipt)` is called at `bot/settle.py` **734–743**. An exception is recorded as a failure, but a returned value such as `{"ok": false}` is not independently rejected. If that callee can signal failure without raising, later successful projections permit acknowledgement despite the reported migration failure. Its implementation was not supplied for this bounded slice, so this is a conditional caller-contract gap, not an established live defect. A separately owned correction, if that return contract permits such a value, should require explicit success and retain the receipt otherwise. A focused regression would inject a nonthrowing failed migration result and prove acknowledgement is not called. It is outside the helper-only repair.

**Projection completion is not atomic.** The order is migration link → position ledger → NAV mark → republication → decision reconciliation → acknowledgement. Position or mark exceptions are accumulated; they do not stop later publication/reconciliation calls (`bot/settle.py` **733–852**). Some projections can therefore advance while another remains incomplete and the receipt remains pending. Receipt retention is the recovery obligation, not proof that every consumer continued to display the same version throughout the attempt.

**An acknowledgement retry repeats the projection sequence.** The exception branch at **855–868** does not persist a separate acknowledgement-only phase. If the receipt remains, a subsequent invocation runs the shared finalizer again. The comment about retrying only acknowledgement overstates the implemented granularity. Same-date NAV replacement is visible in `paper_account.mark` at **3224–3247**; equivalent idempotence of position logging, publication/learning, migration linking and decision reconciliation is not established by this caller alone. Any eventual complete-finalization claim needs a controlled failure/retry receipt showing no duplicate economic or downstream effects. This is not an instruction to execute a live recovery or to inspect every callee for the current clean-state helper review.

**The acknowledgement Boolean is ignored.** The caller at **854** regards nonexceptional completion as acknowledgement, while `paper_account.py`, `acknowledge_settlement_receipt`, **995–1007** returns `False` if the named file is absent. Participating writers are serialized by the enclosing paper lock. A vanished receipt would require an unexpected callee effect or a nonparticipating actor; neither was demonstrated. Keep this as a boundary on the reported `receipt_acknowledged` result, not an assertion that normal receipt ownership is broken.

**Scheduled recovery can wait for market hours.** `settle_open` tests `is_open` before WAL/receipt recovery (**975–995**). Thus an existing committed receipt can wait in this entry point while the market is closed, even though the finalizer selects saved prices. The direct finalizer has no such market-hours gate. A restart does not establish immediate completion of outstanding publication. Actual delay and caller retry frequency were not measured here.
