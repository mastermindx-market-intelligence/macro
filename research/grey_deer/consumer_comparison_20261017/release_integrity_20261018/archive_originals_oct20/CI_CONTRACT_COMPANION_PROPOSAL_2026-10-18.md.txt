## Separate deployment-owner proposal

Three new parametrized functions add **ten proposed cases**, none executed here:

1. `test_deploy_datadog_tag_matches_target_and_restores_prior_bytes`: onboarding present/absent × successful/failed target health, four cases.
2. `test_deploy_transfers_and_restores_reasoning_policy_files`: prior policy directories present/absent × successful/failed target health, four cases; each checks both policy roots.
3. `test_healthy_unchanged_code_does_not_skip_cohort_activation`: missing/pending marker, two cases.

A small opt-in fixture observer records selected fixture-file bytes at each fake service restart, alongside its existing source SHA. This makes positive transfer observable before a subsequent rollback. It resolves and confines each observed path to the private fixture; all existing test functions and their assertions remain unchanged. No second test harness or runtime controller is introduced.

The Datadog cases copy the unchanged real tag refresher into the source fixture and explicitly set `SYSTEMD_ROOT` to the temporary systemd tree and `SYSTEMCTL_BIN` to the fake service command. They exercise the helper/refresher boundary without substituting a custom version-writing script. They do not run the installer. The helper retains fake SSH, host, key, health, Python CLI and service bindings, and the already-reviewed local-rsync peer confinement. Execution of these new cases still requires root's admission; this paragraph describes the proposed test construction, not a test result.

Counterexamples the new assertions are intended to reject include omitting the tag call, passing the old SHA, targeting the default instead of selected service, omitting required reload, excluding either policy root, leaving new policy bytes after recovery, or accepting healthy unchanged code without cohort activation. These are reasoned test distinctions, not executed mutation-test results.
