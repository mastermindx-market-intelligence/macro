## Security adjudication: preference source

Supabase security guidance states `raw_user_meta_data` (exposed as Auth `user_metadata`) is user-editable and **must not be the trust source for row-level security or authorization decisions**. The incumbent `lib/user_prefs.py` and `app/account_prefs.py` use GET user metadata, merge and a full-object Admin PUT. Existing #10104 integration evidence reproduces an unrelated language-save GET/PUT completing after an alert opt-out and restoring a stale `alert_email_optin=true`. Merely validating `alert_email_optin` from that metadata at drain time is not enough for a provable **revocation / zero-send** promise. Treat Auth opt-in as user preference/input, not as sufficient final permission.

**Preferred candidate subject to exact existing owner & independent security review:** add a server-owned, transactionally updated rotation-family activation/revocation **within existing `public.email_prefs`** with enabled (default false), trusted server activation time, and revision. Under reviewed access semantics, only a server callback handling an authenticated user's explicit intent can mutate those fields and must be audited. A Supabase `SECURITY DEFINER` RPC in public should **not** be introduced casually: it bypasses RLS and may default to public EXECUTE; use a privileged server-side transaction or narrowly scoped, reviewed grant/ownership if necessary. The migration should be additive, reversible, and staged **default-off**, with RLS advisor proof and no blanket `anon` or `authenticated` UPDATE authority. This is a candidate, not an executed migration.

### Proposed invariant and negative tests

`effective_permission` at enqueue and last pretransport admit requires *current server-owned family-enabled true*, *matching activation revision on the queued item*, *observation issue time not earlier than activation*, *current independent global email opt-in and family category*, *entitlement*, *suppression/quiet hours* and *current source legal/freshness eligibility*. Unknown/missing => suppress, never approve. Require server-owned opt-out fence **write-readback before** acknowledging success. A delayed stale language-save Auth metadata PUT after opt-out cannot change that fence. Subsequent re-opt-in opens a new revision/time boundary and previous pending rows remain superseded; two concurrent tabs must serialize unambiguously. No backfill of Oct20 events to Oct29 subscribers. Post-final-SMTP effect_unknown remains quarantined; no invented exactly-once messaging guarantee.

**Reviewer gate:** Before any production DDL, verify (1) original auth/preferences owner and schema migration repo, (2) exact existing service-role usage, (3) CAS/transaction proof, (4) RLS/grants/advisors, (5) same-generation no-backfill and opt-out race tests, (6) #10104 real outbox payload schema and mailer semantics, and (7) normal CI+nonauthor security approval and a separate opted-in production user proof. The Chairman's task authorizes normal work but does not mean a half-reviewed live auth schema needs immediate mutation.
