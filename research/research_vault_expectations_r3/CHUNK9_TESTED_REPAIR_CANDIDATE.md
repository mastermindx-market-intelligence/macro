## 3. Proposed changes

### A. Corpus: opt-in strict errors and pre-limit eligibility

`search` retains its list return and default legacy behavior. Two proposed keyword-only arguments let an existing serving caller pass a request-scoped eligible-ID set and request database errors rather than an indistinguishable empty list.

The allowed set is supplied by the existing catalog/tier owner. It is NOT read from public request parameters, generated by an LLM, stored as another permission database, or treated as new source rights. None preserves the old internal unscoped behavior; an empty set returns no results. Invalid supplied IDs are refused.

The SQL membership condition is applied before the final limit, for both text and facet queries. A single JSON parameter avoids thousands of bound variables. No query or source column is altered; generated tickers are not injected into original text. The serving caller catches database failure and returns the existing unavailable response.

This relies on SQLite JSON table support. Official SQLite documentation says JSON support is built in by default from 3.38.0 but can be compiled out. Test the actual admitted deployment; do not infer its capability from the local run. The local candidate refuses a missing/denied JSON capability rather than silently running unrestricted. It adds no Python package or remote provider. [S4]

### B. API: one catalog read, same response contract

An optional internal catalog argument to the existing `_catalog_ids` helper lets the route use one loaded catalog for admission and the existing fixed preview. Tier resolution remains with its incumbent owner. Preview narrowing is intersected with catalog admission before the corpus query.

The response still has `items`, `count`, and `available`. A healthy no-match is available/empty; a failed attempted database search is unavailable/empty. Empty eligibility can be resolved without touching the corpus; that is a result for the authorized scope, not certification of global index health.

The final membership check remains defense in depth. Strict error behavior is opt-in: other Brain/corpus callers using the default retain their old behavior until their owner deliberately adopts the result contract. This is NOT a claim that all Brain paths have been fixed. General invalid-query classification and retrieval completeness/freshness beyond these cases remain outside R9.

### C. Client: distinguish response meaning and bind the complete request context

A request serial handles repeated identical requests. The context includes query, facets, lane, catalog generation/request counter, tier and available principal identity. Older responses cannot replace the active result when that context changes.

A valid empty server response remains authoritative for that scoped query; it is not widened by local union. An unavailable response keeps only the existing catalog fallback and labels it as incomplete. HTTP authorization denials suppress extra local matches rather than broadening access. Malformed success payloads do not become trustworthy empty results.

The candidate checks context before issuing a delayed request and again before consuming it. It does not create retries, polling, provider interaction or a new request-control service. Full application auth/filter/catalog hooks still require integration review; the selected-function tests do not establish automatic refresh after every actual UI event.

### D. Renderer: consume the status

The selected existing renderer distinguishes incomplete search from 'No reports match' and labels fallback results. English and Chinese status copy is exercised. This prevents a status field from being a disconnected implementation artifact.

The tests use controlled DOM objects, not the actual browser page. No redesign, new font, production design token, page navigation or source-viewer implementation was performed.
