## Why the consumer needs an additional known-at check

Original Data OS `VendorAliasTable.resolve` is a **historical naming** resolver. Its native `AliasRow.covers` enforces original `known_at` against the decision cutoff for `NATIVE_REFERENCE_VENDOR='polygon'`, but not automatically for the generic `tiingo` vendor. This is not necessarily a defect in its historically-named-ticker product contract. It means S2 must NOT mistake the answer to “which security carried this vendor symbol on October 9?” for “what evidence about that vendor alias was available **by the original October 9 trading decision**?”

A direct synthetic conformance check using the incumbent Data OS `VendorAliasTable` demonstrated that an invented Tiingo AAPL alias first known **October 11** can return a historical security-ID string for an October 9 request, while the S2 read-only reviewer properly refuses it with `SELECTED_ALIASES_NOT_KNOWN_AT_DECISION`. This is a **fabricated, non-customer test**, not a claim that the actual Tiingo alias table contains that row.

The original `lib.dataos.identity.alias_binding_sha256` serializes the vendor, original vendor symbol, security ID, inclusive start/exclusive end, UTC source-known-at and retained source-evidence SHA. The synthetic S2 checker reproduces **only the self-consistency check** of that already-owner-selected semantic tuple. The original library and S2 checker agreed on four synthetic alias hashes. A self-consistent hash can be forged and does **not** authenticate the owner, listing, Data OS receipt or legal source-use rights. Source `known_at` is conservatively **CEILED** to full microseconds if the vendor supplies sub-microsecond digits; decision cutoff is never rounded forward. This prevents a nanosecond `19:59:59.999999001` source receipt from appearing available at a `19:59:59.999999` decision.

## Exact consumer semantics, no duplicate resolver

`review_tiingo_pit_aliases` accepts a bounded **tuple of already selected owner alias mappings** plus a registered four-symbol cohort, original event date, explicit UTC decision cutoff and a named original identity snapshot reference. It does **not** iterate through competing historical vendors and choose an alias, map Yahoo symbols into Tiingo, or select a preferred revision. It rejects unselected extra symbols, duplicate candidate rows or security IDs, malformed reference IDs, invalid source evidence/content-binding hashes and ambiguous intervals. It surfaces separate negative statuses for absent vendor aliases, missing `valid_from` or `known_at`, aliases outside inclusive/exclusive valid time, and aliases first known after the decision.

**Even four complete, dated and self-consistently signed synthetic aliases produce `OWNER_PIT_CANDIDATES_NOT_AUTHENTICATED`**, not an admitted canonical source. All outputs retain `pit_vendor_aliases_admitted=false`, `original_owner_identity_authenticated=false`, `source_rights_or_monetary_basis_admitted=false`, `market_pilot_admitted=false`, `customer_publishable=false` and all five research and trading authority flags FALSE. The checker is intentionally unable to mint a positive source release; that must originate from the incumbent Data OS membership/rights and corporate-action owners.
