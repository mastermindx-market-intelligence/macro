# F01 — Builder sequence, success measurement and rollback

**Scope:** future implementation guidance for the design candidate. No product code is implemented or authorized by this document. The current reference remains PARTIAL/RIG draft; native repairs and independent qualification are open. Existing source, route, data, preference, save and Brain owners remain authoritative.

## Success measures

The primary user outcome is correct movement between market, exact Company, focused chart and the intended return context while retaining usable local analytical views. Measure correctness before speed. The source specifications and 85 proposed acceptance cases (79 earlier cases plus six supplemental consumer cases) provide the observation sheet; they are not measurements.

| Question | Measurement on a later authorized implementation | Decision rule |
| --- | --- | --- |
| Can users find the intended company/tool? | Matched before/after tasks for exact listing and duplicate-looking directory names; first destination chosen, completion, recovery actions and elapsed time | No wrong-listing or merged-destination error in the designated qualification set. Report success denominator and timing distribution; do not claim improvement from static A/B images |
| Can they understand current location? | Ask the user to identify global job, market, product and local view on mapped and unmapped routes | Correct location without treating Today, a region or an inherited icon color as a second current primary job |
| Does evidence preserve the analytical task? | Open two different field/period/event objects, close/reopen, sort/filter and resize; record actual object identity, selected state, scroll and focus | Correct identity and no loss of retained fields/history. One inspector, protected primary width, named logical return |
| Does chart return work? | Capture entry href, URL-selected symbol, named return URL, browser history, selected view, scroll and focus separately | Each promise has a separate result. Exact URL success cannot conceal failed selection/scroll/focus restoration |
| Do access and writes remain truthful? | Guest/denied/expired/unavailable and pending/failed/uncertain/confirmed owner outcomes using controlled lawful fixtures or accounts | No data exposure through a shell label, no false Saved, no duplicate request from navigation, no uncertainty turned into automatic retry |
| Does narrow navigation retain depth? | Repeat Company, Options and directory tasks at 320/390 and effective narrow width under zoom; include long Chinese labels | Every retained local view and important action remains reachable with a meaningful analytical object; no accidental page-wide horizontal overflow |

For a comparative usability study, freeze identical task/data conditions, record participant locale/device/experience, counterbalance A/B order and retain failed attempts. Timing and preference are different outcomes. Report sample size and uncertainty rather than presenting a small qualitative study as a population estimate. No participant study was run in this assignment. New telemetry events or analytics storage require their existing owners; the inspected search telemetry endpoint is not a general shell-event API.

## Performance budgets and measurement scope

The programme's **proposed implementation targets** are **LCP ≤2.5s, INP ≤200ms and CLS ≤0.1 at the 75th percentile**, assessed separately for mobile and desktop. These are requirements from the [same-pin common brief](https://github.com/mastermindx-market-intelligence/macro/blob/6e1862867193ec6486a22001a0e4fb515da20448/research/design_candidates/production_design_20261102/COMMON_SESSION_BRIEF.md), not current measurements or certification of beta.

Measure cold entry and warm client navigation separately on representative Today, Company, Options and legacy-host routes. Identify the exact deployed/served build, device/network conditions, browser, authentication/access state and fixture-versus-real-data basis. Use field distributions when sufficient legitimate observations exist; controlled lab traces diagnose causes but do not stand in for field p75. Account for failed/retried routes and unavailable data rather than excluding them to improve the reported experience.

Preserve lazy `SharedShellRuntime`/toolbar mounting, deferred company-manifest intent/idle loading, finite directory results, route `no-prefetch`, actual per-key flow subscriptions and domain-specific heavy-view code splitting. Opening one shell utility must not eagerly import every workspace/chart or ship the 13k-route corpus into every first render. Record critical-path JavaScript/CSS bytes, image/font costs, rendered nodes, subscription count and long tasks against the exact prior build. No numeric asset/DOM improvement is claimed here; any intentional regression needs a measured task benefit and owner review.

## Compatibility and migration

Treat the later implementation as a presentation migration through the existing components. Keep exact canonical IDs, `/options` versus legacy Options paths, D07 parser behavior, ordinary query/hash semantics, existing host-generation/registry checks, existing browser/history ownership and all stored object identifiers. The known Options-local `URLSearchParams` reserialization issue requires its owner-qualified decision; it must not be hidden by a shell transport test that never exercises the local action.

Use the existing auth identity and preference owners; email remains presentation. Compact mode remains mounted-instance state unless a separate reviewed migration changes its scope. Theme/locale transitions retain their current persistence semantics and focused Terminal exception. No new save endpoint, retry key, route registry, active-symbol store or global assistant is part of this design.

A directory label proposal is a reviewable presentation input to the incumbent exporter, never a second runtime registry. Preserve old searchable names as aliases when a reviewed name changes, retain exact destinations and access fields, and never turn a display group into route admission or a primary-current mapping. Unclear domain meanings stay with their existing labels until the owner resolves them.

## Rollback and operational limits

A later rollback should restore the previous shell presentation through the existing source/configuration owner while retaining route registry, data schemas, saved objects, request identity and entitlement state. Do not use rollback as an excuse to replay an uncertain write or regenerate user data. Verify that deep links, focused Terminal and legacy direct/original-page recovery remain serviceable after the presentation rollback. This document does not create or name an unverified feature flag.

No rollout percentage, deployment environment, release command or production authority is assigned here. Those belong to the later commissioned implementation/release path. The present useful output is a concrete, source-bound design and builder package with exact held conditions.
