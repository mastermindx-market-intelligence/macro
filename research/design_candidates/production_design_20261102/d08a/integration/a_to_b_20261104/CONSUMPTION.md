## Three integration hazards that remain explicit

### 1. A valid pin key does not prove required provenance

The fresh protected Terminal read at **f528a219cc5d73e94e058575e3df83d689632bf9** retains shortlist blob **8d42da79f3e5bbda9ea236df93845824feb4900d**. Its executable pinKeyFor is family + session + identityKey. buildPin retains hotView separately and allows it to remain null. addPin returns the existing pins when the key already exists.

Consequently:

- Retain the actual source-list context independently through existing owner mechanisms; do not infer it from the key, current tab or a copied label.
- If provenance is missing, name the missing evidence. Do not fabricate a list or insert extra fields into the closed pin/draft payload.
- A second hot view of the same family/session/contract focuses the existing frozen pin. It is neither a distinct contract nor an implicit source refresh.
- The full original unfiltered list remains necessary for ambiguity validation. It must come from the same reader/source generation as the selected row.

This settles the A/B/C design interpretation of original G04. D08's integrated adoption and actual caller behavior remain open. G04's historical passing characterization is not rewritten into an implementation PASS.

### 2. locatePin(...)=present is not exact-original return proof

The same current module's locatePin checks whether a current-list row has the pin's contract identity, then checks the root filter. It receives no current source envelope and does not compare source session, digest, correction identity or original bytes.

A later or corrected observation of the same contract can therefore satisfy that presence lookup. This is a source-inspection finding, not a newly executed runtime test.

The return path must separately qualify the originating family/list/session and revision where available. Keep the frozen origin and identify a newer matching observation as current context. If the original observation or original bytes are unavailable, say so and use the existing named scan/focus fallback. Do not select a nearby row, silently overwrite the source snapshot, or make locatePin a temporal-evidence validator.

### 3. Preserving origin does not override access loss

Keep protected source values under their existing source/access owner. The shared returnContext is navigation metadata, not a hidden evidence cache.

After principal or entitlement change, clear protected prior-context values and ignore late old responses through the incumbent request/cache owners. Retain only lawful identifiers/navigation context. Original source evidence can become unavailable, while a permitted return to the scan or named fallback remains useful. No new auth, cache, history or persistence plane is proposed.
