This is the Chairman's design-only upgrade programme for the whole Mastermind website, including the shared shell at https://beta.mastermind-x.com/. Complete the assigned product design, Paper organization and product/backend/build specifications. The Chairman will deliver the splitoffs and return for independent re-audit before commissioning implementation. A session must not stop after drawing a polished desktop screen.

Use the existing whole-estate charter: `research/MASTER_PRODUCT_SHELL_MAKEOVER_MIGRATION_2026-10-08.md`. This package is its dated subsidiary task tree. It is not a new umbrella workstream; WS:MARKET-OS remains a consumer. Use relevant existing domain workstreams for actual domain decisions. Design candidates belong under `research/design_candidates/production_design_20261102/`; do not place unapproved prompts in `research/migration_packets/MP-*.md` where approved RIG receipts are required.

At launch, use bootstrap-mastermind and paper-design-workflow, read the current protected INDEX and required procedure files at one verified SHA, and record that pin. Use the audit pins as evidence, not a substitute for current source law. Re-read only assigned source/Paper targets and known overlaps for drift. Do not repeat the entire census. Honor existing holds, rejections and live writers. Manual attended Astra Pro delivery does not require inventing an automated Pro receipt or changing model modes. Route eligible routine labor through the existing paid Fabric process only when actually admitted; never fabricate grants or lineage. Native principal critique is not a substitute for required review admission.

Resolve this package's publication branch to one immutable commit at launch and read the brief, common instructions, crosswalks and acceptance checklist from that same commit. Record the package pin. Do not mix moving branch revisions. Later F01/F02 contracts are separately versioned and reviewed dependencies.

The observed Paper write-schema qualification is false. Reads and source/specification work can proceed. ## Required work sequence

1. **Establish the real product.** Inspect the served site where accessible, current source, all assigned route/query variants, current Paper candidates and predecessors. Record browser access limitations explicitly. Compare existing capabilities with proposed designs; do not use a page title, empty frame or screenshot count as coverage.
2. **Write the product brief and retention ledger.** State the primary user, question, outcome and complete journey. Give every capability `RETAIN`, `IMPROVE`, `RELOCATE`, `REMOVE` or `BLOCKED_DATA`. A relocation needs a reachable successor. Removal needs product rationale and applicable decision authority. Unsupported data needs a named dependency and useful interim state. New ideas are labeled proposals until their backend and product ownership exist.
3. **Resolve the information architecture and contracts.** Decide which repeated features should share an object/pattern and which meanings must stay distinct. Preserve route aliases, query parsing, source identities, access boundaries and regional differences. Reuse existing strong references; full RIG is for flagship/hierarchy changes, while local cleanup may use the existing lightweight path.
4. **Compose within frozen foundations.** Consume F01 shell v1 and F02 system v1. F01/F02 themselves develop and freeze the joint contract; they do not wait for their own unpublished output. Work can begin on baseline, retention and contracts while these are being settled. Do not freeze a domain candidate with provisional global chrome. Escalate a required shared change to its owner with a concrete example; do not fork the shell.
5. **Finish the actual experience.** Produce editable references, real content density, purposeful charts/tables, transition and state specimens, responsive/theme/locale coverage, and annotations adjacent to the relevant controls. Illustrative numbers must be marked and tied to field semantics, not presented as validated backend output.
6. **Prepare the builder package.** Identify actual source entry points and producers, reuse/replacement boundaries, integration sequence, acceptance conditions, migration/rollback and unresolved dependencies. Provide enough information for a future builder to implement the intended behavior without inventing product rules.
7. **Review, fix and return.** Supply before/after evidence and user tasks to independent product-regression and visual/taste critics. Keep designer rationale out of the first pass. Resolve findings, freeze exact references and return the evidence/status in the standard form. Do not self-certify full production readiness.

## Deliverables required in each product file

Create a `00 · Read me & Build contract` page with a plain product description, task flow, current canonical candidate links, source contract link, owner, shell/system versions, limitations and review status. Add concise specifications beside screens for primary controls, transitions and exceptional states. A single external link without useful in-Paper explanation is insufficient.

All materially changed shell compositions, hierarchy and interactions must have editable Paper references. Raster captures and source-backed implementation specimens remain supporting evidence. Reuse without reconstruction is allowed for an unchanged reference with actual approval evidence; any new shell composition around it is still an editable design obligation. This prevents the GMI task from ending with another set of website screenshots.

The complete source package must contain:

- **Product brief:** persona/job, key questions, scope, complete success journey, proposed improvements and success-measurement plan. Do not claim measured usability without evidence.
- **Capability ledger:** every existing feature, baseline route/Paper reference, disposition, successor, justification, dependency and reviewer decision. Include deep pages and hidden drawers/tabs, not just the first fold.
- **Route and object map:** canonical registry IDs; aliases, path/query/hash variants; page host/product; entity/company/listing identity; regional availability; access/entitlement boundary; exact source template/component/builder.
- **Interaction/state contract:** control/action, precondition, resulting state, route change, source write if any, feedback/copy, keyboard/touch behavior, focus/scroll return, pending/failed/uncertain outcome and recovery. A navigation action must not silently mutate saved state.
- **Data/backend contract:** actual producer/API/file/schema and owner; fields/types/units/currency; entity keys; observation/publication/ingestion clocks; cadence/cache/TTL; point-in-time/revision behavior; zero/null/unknown/stale/partial semantics; auth and server/client responsibility; mutation/readback/deduplication; unavailable dependency. A proposed endpoint is labeled proposed, never written as an existing API.
- **Design/component map:** exact Paper file/page/artboard IDs, editability/source-capture distinction, theme/locale/width/state, shell slots, F02 components/tokens, intended motion/reduced-motion and chart/table alternative access.
- **Builder plan:** code entry points, reusable modules, shared-template ownership, actual content widths, implementation sequence, compatibility/migration, meaningful tests, performance budget, rollback and intentionally unresolved decisions.
- **Review and return:** exact frozen references, before/after screenshots, regression and taste findings, remediation, source commit/PR, RIG status and remaining owner actions.

## Quality floor

The first useful view must answer the main question and offer a clear next step. Prefer one primary analytical/reading object and no more than two supporting modules above the fold where that serves the task. This is a hierarchy discipline, not a reason to delete functionality. Preserve visual information compression: a useful chart, matrix or comparison table is not replaceable by a paragraph wall.

Test representative viewport classes at 320, 390, 768, 1024, 1280, 1440 and 1600 CSS pixels and measure the **available content width** after shell/inspector. These are evaluation points, not seven mandatory duplicate full-screen atlases. Include long labels, EN/ZH, light/dark, selected/focus/hover, 400% zoom/reflow, keyboard-only use, touch and reduced motion. For complex 2D charts/tables, contain necessary horizontal interaction within the component and provide a meaningful accessible path; do not excuse whole-page overflow.

Use the programme's 44px house target for important mobile controls. WCAG 2.2 AA target-size minimum is 24×24 CSS pixels or applicable spacing/exceptions; do not misstate 44px as that AA rule. Verify contrast and non-color state communication. Current design doctrine prohibits colored container borders/accent stripes; focus outlines remain legitimate.

Include loaded/success, loading, empty-with-reason, partial, stale, unavailable/unsupported, error, guest, denied/plan-required, expired-session, first-use and save-pending/saved/failed/uncertain where applicable. Explicitly mark a state not applicable and explain why rather than creating meaningless duplicates.

Proposed implementation targets are LCP ≤2.5s, INP ≤200ms and CLS ≤0.1 at the 75th percentile, assessed separately for mobile and desktop. These are future budgets, not measurements from this audit. Specify lazy mounting, bounded subscriptions and rendering responsibility; do not eagerly load all routes, all charts or hidden workspaces.

## Acceptance and reporting

Project the existing RIG states: `draft`, `in_review`, `approved`, `revise`, `rejected`, `superseded`. Keep reference acceptance separate from implemented, merged, deployed and served-proof status. Do not create an invented RIG receipt or assign an approved state without the actual required review.

**Immutable review freeze:** record exact Paper file/page/artboard IDs and observation time. Retain supported exports/captures of the candidate, its annotations/specifications and verification screenshots in the source package. Bind the existing RIG manifest/receipts to that committed artifact set and its required SHA/digests. A mutable Paper URL, snapshot guard or token content hash is not an immutable document revision or approval identity. Later canvas changes require affected exports/evidence and review to be refreshed. Carry every unresolved predecessor blocker and authority condition through the existing RIG continuity dispositions: RESOLVED_BY_CHANGE, CARRIED_BLOCK, OVERRIDDEN or SUPERSEDED with the required evidence/authority. CARRIED_BLOCK cannot coexist with approved.

The first-pass critic input set is closed: user/business job, production-before artifact, proposed-after artifact and capability/task manifest only. Reveal designer rationale, constraints and data limitations after the first-pass findings freeze and record second-pass amendments. Access limitations are evidence gaps; they are not designer excuses supplied in advance.

P00/F03 must distinguish SUCCESS from PARTIAL/BLOCKED_RETURN. An unapplied organization plan or unqualified adapter is not completed merely because its blocker has a well-written record. P00 may prepare the established adapter repair and carry the original-owner review/deployment path only where existing authority/admission covers it. This exception concerns infrastructure repair, not product implementation or rollout. Otherwise return the concrete fix and exact owner dependency.

Return exact changed IDs/URLs; source commit/PR; candidate and predecessor; shell/system version; capability disposition counts and all removals/relocations; completed journeys/variants; backend/route gaps; review findings and status; remaining work with named owner. Record checkpoints if interrupted. A completed local phase is not a reason to abandon the rest of the assigned brief.
