## Compatibility contract

| Reader | Response | Expected result |
|---|---|---|
| Frozen older v1 reader | New v2 response, including changed recipe/identity | Reject before replacing protected walls |
| Current v2 reader | Prior receipt-bearing v1 | Reject; existing access check can recover with valid v2 |
| Current v2 reader | Legacy unbound v1 | Reject |
| Current v2 reader | Matching valid v2 | Existing authorized hydration succeeds |
| Current v2 reader | v2 with a different full-source receipt | Existing generation-mismatch state; reload the page |
| Current v2 reader | Sign-out after valid hydration | Restore walls and retain public evidence through the existing lifecycle |

The full source hash already binds the recipe. A second recipe identifier would duplicate identity rules. Version and source receipt solve different questions: whether the reader understands the contract, then whether the response belongs to the page's source.

During a rolling update, either mismatched version pair refuses hydration. This is a fail-closed compatibility property, not proof of an atomic or deployed rollout. A version fence cannot remove names that an old reader already painted before the transition.
