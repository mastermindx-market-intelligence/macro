## 3. U31: save semantics, uncertainty and existing persistence

### Implemented behavior

Candidate `prophet_save.js` captures the source row, exact native link, DOM occurrence, source stamp, Today binding, source mode, grid/table view, user id and auth generation. It calls `checkedSession()`, reads actual account lists, and uses `saveChecked(listId,[ticker],{returnFocus})`. It passes **no `decisions` payload**: this is membership Save, not an immutable thesis save. Empty lists send the user to the existing Watchlists surface; there is no speculative list creation on a failed read.

On save start it adds a hold to `unconfirmed` before invoking the owner. A successful result requires `state:'saved'`, the requested ticker in `names`, and `readBackAt`. Known refusal clears the hold. Any timeout, lost response, unexpected result or missing confirmation keeps it. The guard is memory for the lifetime of this page. In the same page it conservatively holds any Save of that ticker for that account, even if the user tries another list; it is not a durable operation record across reload, tab loss or another device.

`WatchStore.symbols.inspect(listId,symbol)` is already in main. It reads exact owned list then exact membership, with auth epoch/client/uid fencing and a deadline. Result fields are `state`, `membership`, `listId`, `symbol`, `listName`, `observedAt`, `readRetryAllowed`, `writeRetryAllowed:false`. States include `present`, `not-confirmed`, `unavailable`, `no-session`, `stale-session`, `invalid`. It does not clear the original write, mutate the outbox or allow retry.

**Two facts may coexist:** the user's desired membership is now observed, while attribution/outcome of the earlier insert remains unknown. Show “In your list · checked at …” as a present postcondition and retain the unresolved operation separately. `not-confirmed` is not proof of no effect and never re-enables the original write. The candidate already says “This read does not prove the earlier save” and leaves the hold intact.

### Specific integration gap

Main has `inspect` and `saveChecked`, but no `checkedSession`; candidate-only `prophet_save.js` assumes it. Copying that adapter alone gives an unavailable Save. Copying the entire candidate WatchStore over main could lose later owner work. Integrate the exact checked-host/readiness/account-scope additions selectively against current main, with the incumbent held diff and writer controls preserved. Auth scope must be captured when enqueueing, not when an earlier per-list operation finishes. Candidate `_finish` redacts stale-session identity and returns uncertain if any request left, rejected only if none did.

The original checked Save path deliberately avoids the legacy generic sync outbox on ambiguous write. Do not route it through `symbolAdd`, generic retry/fold, or a fresh queued write to “recover” uncertainty. Extend the **existing checked Save owner** with bounded original-request custody/readback if reload-resilient uncertainty is promised. Define durable operation reference, immutable owner/list/security target, attempt boundary, outcome state, authoritative observation, and which existing actor may reconcile. This analysis does not invent a new endpoint/table/queue or prescribe unreviewed storage.

### Persistence and migration facts to preserve

- Schema owner is Terminal `supabase/migrations/0001_init.sql`; `0009_watchlist_symbol_unique.sql` owns unique membership. The source comment records past production application; verify deployed schema only when integrating, without reapplying migrations by assumption.
- Terminal `writeMembership` uses conflict-target upsert. It has a loud legacy missing-index fallback; this is not proof of uniqueness in an arbitrary environment. Macro `saveChecked` comments still say no unique index. Resolve that stale source/documentation mismatch through exact deployed-schema evidence before claiming cross-client concurrency safety.
- Terminal `watchlistOwner.ts` already owns per-account local storage (`mm.wls.v2`, flags, notes, migrated receipt and tombstone envelopes). Preserve identity-keyed cache isolation, source migration receipts and deletion behavior.
- Terminal `watchlistAnnotations.ts` (blob `bf9d1562f9e2d57024619c51558c2c5ff58a875d`) and `0033_watchlist_annotations.sql` already support bounded cross-device note and flag fields, each with independent revision CAS. Required owner header is `x-mm-annotation-owner`; incomplete reads carry `complete:false`. Notes are user text, **not source facts or a dated research thesis**.
- Do not use Macro WATCHLIST.md's older “all notes local only” prose to erase Terminal's newer annotation owner. Conversely, the annotation table is not an unbounded container for evidence, model policy, milestone or immutable research snapshots.
- A future saved investigation remains an owed capability: exact listing/occurrence/generation, saved evidence revision and receipt, author intent, correction/supersession, owner account, visibility and readback must be assigned to the accepted existing research/decision owner. Membership or a 500-character symbol note does not satisfy it. Terminal research handoffs already reference versioned investigations; that sharing projection is not proof of a Prophet investigation-save path.

## 4. Compare and return: preserve the useful source, close the actual design gap

Current candidate Compare is narrower than the Paper specification. It operates on 2–3 live `.pvcard.pv-has-setup` rows within **one** `#us-today-grid` or `#us-cand-grid`. Choosing another grid clears the selection. “Compare selected” hides unselected cards, retaining native DOM order; it does not build an aligned comparison matrix or table/off-filter selected-object panel. It explicitly says strategy and holding periods are not supplied. Do not report the Paper mobile retained-selection or aligned-field view as already implemented.

Extend the existing transient owner with a bounded selection of listing identity plus occurrence/episode identity plus generation/receipt. Keep `selectionOrder` distinct from `sourceRank`. A filter can hide a selected row without changing selection: show “Selected outside this filter” and a deliberate Remove action. An entitlement loss, identity mismatch or generation replacement makes a selected object unavailable until an explicit recovery; it must not silently bind to a same-ticker replacement. Distinct episodes of one listing remain distinct choices; unsupported identity never becomes a ticker-only dedupe.

Comparison rows must show actual supplied strategy, horizon, observation clock, quote/series clock, entry read, strongest support/challenge and coverage; differences in unit/window/strategy must remain visible. Unknown fields are explicit. There is no justified universal “best” column. Mobile can select two visible columns while preserving the three-item selected order; keyboard controls and a numeric data alternative are mandatory.

The existing return owner is unusually valuable and should be retained. Plan navigation first calls `USProphetLife.selectPlan(card)` while the candidate is still open. If the exact record is missing/withheld, candidate section, focus, view and scroll stay put and a local error explains it. Only after native target resolution does `PVSetupReturn.snapshot` capture origin mode/view, nodes, ticker/native href, source stamp, Sources section, Plan-link control and dialog scroll. Return restores that origin and the original Plan-link focus when still valid. The return token is invalidated on node/source/access changes, unrelated navigation or target removal.

Do not weaken this into “return to ticker.” The next extension can retain a safe dated reference and offer “Open current research” or “Keep this dated view” only when an authorized retained snapshot really exists. Current in-memory DOM state is not a durable dated snapshot. Never fabricate a snapshot after its source disappeared or entitlement was revoked. Browser reload/history restoration needs an explicit existing-route serialization contract; source-safe focus return within one page is the implemented baseline.

Closed emitted kinds are `episode_terminal`, `emergence_triggered`, `corrected_material`, `retracted`, `superseded`. OPENED, unchanged observation, quote refresh, unknown/missing state, ordinary freshness change and B4 availability changes are not supported event kinds. Eligibility is producer-issued. The fixed logical identity is:

`prophet|kind|episode_id|from->to|b1_event_id|user_id`

Nightly candidate generation and definition era belong in provenance, not dedupe identity; inserting them in the key would notify again for the same logical event. Corrections refer to the original `corrects_fire_event_id`, with original outbox status and unknown-effect handling retained. The actual source has this logic; do not replace it with frontend date comparison or a new event registry.

Current preference categories are holdings_material_change, thesis_window, fif_saved_issuer, options_exposure_node, sector_rotation_relative and cs_saved_scenario. **Prophet's category is absent.** B21's pure producer and the drain's generic `not_after` guard exist, but this does not establish the IO runner, actual enrollment, supported UI or delivered Prophet notification. ## 6. Transport and entitlement composition

Terminal already has a sufficient Early Observations transport seam: `/api/prophet/observations` → fixed Macro `/api/prophet/observations/v1?ticker=…&limit=50`. `billingAuthResult` obtains verified session identity; Macro remains entitlement/observation authority. The BFF uses private no-store, Vary Authorization/Cookie, redirect refusal, a 10-second request deadline and 128 KiB body bound. Its decoder requires `prophet.early_observations/v1`, US identity, matching dates/receipts and all six authority booleans false (`buy,alert,entry_open,rank,size,episode_write`).

The single `useProphetObservation(active,userId)` call is wired in `TerminalShell.tsx` (blob `46303cc2c47756a88165f1a530e7b8ae5ccb4a67`) and passed to SignalButton and OracleDash. It clears outgoing account/symbol synchronously, sequences late responses, listens to native auth, and refreshes on actual visible/focus edges with a 60-second discipline. It creates no extra interval/cache/watcher. Extend this seam rather than adding another auth or data-fetch authority.

Its statuses are loading, ready, unavailable, unauthenticated, forbidden and unsupported. Distinguish current-session from retained-previous-session data, universe absence from in-universe/no recorded trigger, unverified coverage from zero observations. A new Screener API need should extend the existing native candidate/observation owner; do not treat this single-symbol 50-row consumer as proof of complete paginated search.
