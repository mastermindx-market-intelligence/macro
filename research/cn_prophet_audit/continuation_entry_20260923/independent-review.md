RESULT:
The continuation/freshness guard is, as a piece of source logic, substantially sound and unusually well pinned by tests: fail-closed on missing/stale/future/non-session `as_of`, on duplicate theme ids, on missing or malformed member observation, on non-`bool` typing, on demotions, and on source conflict — and I could not construct a case where a defensive (`reduce_avoid`) source read is promoted into displayed Buy Now, nor where a tape/cycle observation originates a buy. No new palette, no new CSS, and no runtime-JS stylesheet is introduced by this candidate, so there is no design-system bypass here.

It is not a PASS. Three material findings stand, and the dual-theme evidence matrix does not cover the states this change actually adds.

**1. (major — correctness/production) The freshness gate is strict-equality against a 17:00-CST-settled clock, and the main path never passes `observed_at`.**
`assemble_act_now(..., observed_at=None)` defaults to `datetime.now(timezone.utc)` (`engine/china_act_now.py:303`, `:693`), and `scripts/build_china.py:1398-1404` calls it without `observed_at`. The gate requires `day == cn_calendar.expected_last_session(now)` exactly (`engine/china_act_now.py:702`), and `expected_last_session` only returns *today* after 17:00 CST (`lib/cn_calendar.py:47`, `:188-190`). Therefore a board baked in the 15:00–17:00 CST post-close window against a `baskets.json` whose `as_of` is *that day's* session (`engine/theme_scoring.py:1508`, `as_of = idx.max()`) gets `session == T` vs `expected == T-1` → every THEME row flips to `status: UNAVAILABLE`, Buy Now empties, and all theme chips become "DATA UNAVAILABLE" — on the freshest possible data. The direction of error is safe (no false buy), but it is a whole-board user-facing outage driven by render wall-clock, not by data. Every test clock is 10:00 UTC = 18:00 CST (`tests/test_china_act_now.py:984`, `:1102`, `:1139`, `:1253`), i.e. entirely inside the post-settle window; the pre-settle window is untested and unproven.

**2. (major — hidden affirmative claim after guard failure) The `UNAVAILABLE` guard clears only the recommendation words; every other affirmative figure on the card survives.**
`engine/china_act_now.py:761-765` sets only `reco=None, reco_en="DATA UNAVAILABLE", reco_zh="数据暂缺"`. The row keeps `score`, `rel20`, `rel5`, `breadth_pct50`, `leaders_*`, `reasons`. The template then still renders the score chip, including the green `anv2-score-hi` class at ≥60 (`templates/_china_act_now_board.html.j2:220`; `templates/theme.css:1665` `.anv2-score-hi { color:var(--ink-up) }`) and the signed relative-performance line in up/down ink (`:251-258`). In the hover decision card the same stale numbers are rebuilt into the stats grid and the score ring (`:83-105`, `:179`), the kicker still reads "Current read"/"当前判读" (`:180-181`), and the `sub` line still prints the stale theme reasons (`:194-195`) — all sitting directly under the override read "Current inputs unavailable" (`:74-77`). So a card that declares its inputs unavailable simultaneously publishes a green 65 and green +1.5%/+3.7% with no staleness marker. The guarding test only asserts the absence of two prose strings (`tests/test_china_act_now.py:1221-1224`); it does not assert the stale score or perf figures are suppressed or marked. This is exactly the "hidden affirmative claim after guard failure" the commission asked to be tested for, and it is present.
