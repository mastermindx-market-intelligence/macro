## A — Product thesis and acceptance ruler

### Chairman job

Assign a consequential outcome to Sol once, then receive correct decisions and accepted results without routinely finding the right tab, carrying messages, selecting accounts, copying context or restarting the company’s reasoning from memory. Chris retains strategic, financial, credential, irreversible-action and other genuinely reserved decisions. Removing those legitimate decisions is not the goal.

### Machine job

Keep one durable responsibility connected to the current authoritative actor, its allowed tools, active children, material returns and unresolved effects while conversations and provider processes are replaced. Preserve exact identity, provenance, correction history, authority, time and effect state across every transition. A browser conversation is a coordinate, not the CEO office.

### Moat

The moat is the correction-safe accumulated relationship between outcomes, architecture decisions, company responsibilities, evidence, implementation and observed results—and the ability to use those relationships productively. Neither a browser plugin nor a transcript archive is that moat. The long-run reference architecture already states this thesis; this packet closes its missing connections rather than replacing it. **[R11]**

### The 10/10 experience

Today shows whether meaningful action is needed, who is accountable, what material exception exists and what evidence supports the claim. Advanced/Web Sessions shows the operational details when needed. An admitted worker can finish and return while Web Sol is absent. A return reaches the exact current Sol through accepted attention/Dialogue owners. A failing conversation is diagnosed only to the degree necessary to decide safe continuation. If succession is justified, one exact successor recovers the company state, proves readiness through an accepted channel, receives the current binding, fences the predecessor and performs the next useful governed action.

Completion requires the complete reference journey, not a dashboard screenshot or a collection of merged libraries. The target metrics are zero **routine** Chairman message shuttles, tab hunts, account selections and context reconstructions after commissioning. Count real strategic/admin approvals separately rather than hiding them. **[R11, R12]**

This is an integration freeze **proposal** for the accepted owners, not a new runtime or law already adopted.

```text
Chairman
   |
   v
Today / Ask Sol (only when grounded) / Advanced                 [Control Room]
   |    exact evidence + exact navigation, no lifecycle writes
   |
   +--- responsibility, decisions, discoveries, handoff -------- [Agent OS]
   +--- Job / Attempt / Worker / Event / CEO admission ---------- [Executive OS]
   +--- logical target / current epoch and generation ---------- [SessionTarget + OHF/RuntimeBinding]
   +--- eligible host/account/model/resource ------------------- [Capacity / existing Fleet owners]
```

**Authority flows downward from the current accepted owner; evidence flows back upward.** A model response, browser receipt, title, hostname, profile nickname, Git merge or Slack delivery cannot elect an actor. The dashboard composes the owners’ records; it does not resolve conflicts by choosing whichever source is convenient. **[R01, R06, R07, R11–R17]**

### No-rebuild boundaries

No Connected Office OS, new workstream, session database, transcript store, inbox database, quota ledger, queue, browser elector, permission server, retry ledger, new supervisor or universal super-MCP. Any adapter-local cache/handle is ephemeral transport state, never a second authority. Fable consumes existing source custody, runtime operations and proof owners. More app permissions or a more powerful model does not expand its organizational grant.

### Delegation while the Web leader is absent

Already-admitted bounded work should continue through the existing Executive/COO cycle and external workers. A returned result remains durable and pending the correct principal’s judgment. A closed chat does not stop a valid worker; it also does not authorize a worker to self-mint its next mission. The existing offline-delivery source work is the correct owner for this independence, not an API Meta-CEO replacement. **[R33, R39]**

### Platform qualification is part of architecture

OpenAI’s current custom-MCP documentation distinguishes Pro read/fetch from Business/Enterprise/Edu full modifying support. An available curated app must still be judged from its actual schema and permissions; this distinction is not a blanket claim that every Pro-installed app is read-only. Fresh conversations may require app selection/approval and must prove the exact tool generation. Do not disguise a write as a read or rebuild an auth plane to evade that boundary. **[W02]**

The reviewed Projects documentation supports project context and connected apps, but does not establish a durable successor-creation/first-submit transaction or exactly-once identity contract. Those are empirical/provider-contract gates, not values Astra can infer. **[W01]**

Individual-use terms prohibit automated extraction of data/output, account sharing and bypassing restrictions. That is not evidence that this particular run was restricted. ## H — Context Rotation closure: exact transaction and missing verticals

### H1. Classifier

Use the required closed states: SESSION_HEALTHY, ROTATION_SUSPECTED, ROTATION_REQUIRED, AUTH_REQUIRED, PROVIDER_TRANSIENT, SURFACE_UNUSABLE, UNKNOWN. Separate state from reason and observation time. A generic Thinking failed event permits at most a suspected/unusable/unknown classification unless stronger evidence exists. Do not claim knowledge of internal context tokens, cause, model effort or an account limit from a spinner or failed response. **[R05, R12, W03]**

A rotation decision can be justified by inability to safely continue the exact responsibility without claiming a specific internal exhaustion cause. Thresholds and admission must be frozen under existing continuity/health owners, not a model-authored “looks stuck” heuristic that acts autonomously.

### H2. Pre-effect reconciliation and candidate authority

Before creating a successor, resolve current predecessor binding and open effects through their actual owners. EFFECT_UNKNOWN stays attached to its original operation. Read-only recovery may proceed, but the successor cannot retry an unknown write, replace the worker or move the job to another account.

The candidate receives **recovery/readiness-only** scope, not the current writer’s full authority. This breaks the apparent bootstrap paradox: it can recover canonical state and acknowledge exactly what it received before the binding transfers. A pre-cutover START, if the accepted Dialogue contract requires one, must mean a later separate readiness/continuation step under that limited grant—not permission to perform the predecessor’s modifying work. CB-D0 must bind this meaning to the real existing Executive consumer. **[R07, R13, R14]**

### H3. Provider falsifier before mutation-protocol freeze

Reuse #338/PF-1. First qualify the disposable account/profile/Project and supported policy/interaction channel. Measure when the durable conversation identity appears, whether blank new-chat navigation creates durable state, whether first submission creates the chat, same-Project membership, duplicate/renamed titles, outside-Project behavior, refresh/back/forward and auth/transient cues.

The preferred implementation is **one physical create-and-bootstrap transaction when the provider couples identity creation to first submit**, represented honestly within the existing operation/effect model. If the provider instead gives a separately durable blank successor, use separate create and bootstrap steps with exact receipts. This branch is a declared provider-fact dependency, not license for the coder to guess. Do not create a successor merely to reserve a title or search by newest chat. **[R12, R41, R44]**
