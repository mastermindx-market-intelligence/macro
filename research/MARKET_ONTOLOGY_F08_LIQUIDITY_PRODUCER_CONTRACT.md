# F08 per-stock liquidity producer contract

MO-PAID-036 / MO-DELTA-014 needs a qualified per-stock input for actual-holdings risk readouts. The native owner already exists: `engine/liquidity_chip.py::compute` computes the 20-observed-session median of close times share volume and its existing tiers/build heuristics. The separate legacy 21-day mean, board metrics, scoring and UI keep their existing behavior.

The stock-library writer adds `liquidity_profile` to its existing per-ticker JSON. `scripts/stock_liquidity_profile.py::write_record` is the directly testable one-record publication seam used by `scripts/build_stock_library.py`; there is no second store, risk formula, collector, public page or user-state read. The engine job moves its existing late cold-runner raw daily R2 restore into the preamble before its dashboard/stock-library builder, with one bounded restore shared by consumers; the collector and its gated publication remain the original owners. This closes the materialization ordering gap without launching new collection. Terminal Portfolio PR1044 retains its route/UI and actual-holding consumer scope. This producer release does not claim full MO-PAID-036 acceptance.

The qualified projection requires raw close and raw share volume from the existing `equity.bars.daily.massive` store, the exact 20 NYSE sessions through the completed-session cutoff, finite valid values, source fingerprint and explicit USD evidence covering that window. The native formula and thresholds are reused unchanged. Current-only currency reference, country/ticker spelling, a profile financial currency and an adjusted-price proxy cannot establish this quote-currency window. Missing information yields null metrics and null `thinly_traded`, with a typed coverage/unavailability reason. An unknown value is never a false thinness flag. The raw producer currently fills missing source volume with zero; its parquet cannot distinguish that from real zero activity. The reader therefore refuses a qualified window containing zero instead of treating erased missingness as observed turnover.

Licensing is already recorded in `research/licenses/MASSIVE_ENTITLEMENT_RECORD.md`: the operator-confirmed enterprise instrument covers daily bars, derived redistribution, export and portfolio analytics. This release records adoption of that existing evidence, grants no new access, exposes no confidential agreement, and gives no forecast, ranking, sizing, gate or trading authority. The Yahoo `equity.bars.daily.stocks` contract remains adjusted and redistribution-not-granted; it is not a fallback.

Clocks remain separate: `source_asof` is the actual final daily bar; `recorded_at` is this projection's observed build instant; `store_updated_at` is only the native store manifest stamp. A manifest rewrite does not establish ticker ingestion, first publication or historical availability. `ingested_at`, `published_at` and `known_at` remain null when not evidenced. Filesystem mtime and source stat tokens are not freshness or content hashes. Currency evidence retains its own source date and validity bounds.

Read states follow F08's native vocabulary: `READ_OK` only for qualified values, `READ_NO_COVERAGE` for missing/insufficient/unqualified coverage, and `READ_UNAVAILABLE` for malformed/unreadable input. Zero activity is not silently interpreted as a liquid or illiquid instrument. These are descriptive turnover/build heuristics, not order-book depth, independent episodes, causal estimates, executable-size guarantees or forecasts.

## Dated currency and source availability adoption

The next slice adopts 20 separately dated `/v3/reference/tickers/MU?date=...` responses captured through the existing configured stocks-reference client. The official [ticker-overview contract](https://massive.com/docs/rest/stocks/tickers/ticker-overview) defines `currency_name` as trading currency and documents the date parameter; its SEC example also demonstrates why that date cannot establish first publication. Every retained raw response has its own request/response observation clocks, exact requested session, ticker and content digest. The dated currency block fingerprints the complete envelope as canonical JSON (sorted keys, compact separators and ASCII escaping), explicitly labelled `source_digest_basis`; that digest is not the original receipt file byte hash. Each response digest remains the hash of its retained UTF-8 body. The `date` query is retrospective reference information, not proof of historical first availability. No continuous validity interval, historical `known_at`, publication time or prospective identity adoption is inferred. The existing six-field explicit-validity input remains supported where independent evidence actually supplies it; the new intake does not manufacture those bounds.

The installed `macro-live-breadth.service` explicitly binds `/etc/macro-live.env`; a bare Python process that does not load that service binding is not evidence of missing provider credentials. One bounded capture on 2026-10-20 returned all 20 MU stock-reference responses for 2026-09-21 through 2026-10-16 with USD trading currency. This uses the stock-reference endpoint only, never the retired options entitlement. The retained source is `data/stock_currency/MU.json`. It is the sole initially admitted ticker; other names retain typed unknown values. The existing engine reference-refresh step can maintain this input with the same provisioned client: at most 20 requests, no retries or redirects, stop on provider refusal, and preserve prior evidence if incomplete. It launches no bar collector, identity protocol or new schedule.

Massive's [daily-file documentation](https://massive.com/docs/flat-files/stocks/day-aggregates) specifies approximately 11:00 ET the following calendar day. The reader therefore separates the latest completed market session, the source schedule's expected session, and the actually observed final bar. It requires the source to meet that availability floor, accepts an actually observed newer completed session, and still rejects incomplete windows and future rows. This schedule is an approximate coverage contract, never a source publication timestamp or a provider health verdict. At early UTC 2026-10-20 the completed market session is October 19 while the source floor is October 16. The profile is explicitly descriptive as of its selected source window; its clocks and zero trading/ranking/gate/sizing authority remain unchanged.


The incumbent `scripts.publish_r2` supports an explicitly selected stock record through `--dirs stockdata --no-manifest --stock-ticker MU`. The optional `--stock-source-file /explicit/path/MU.json` uses one regular source record while preserving the configured native stock file; it requires that same selector and flags, the exact matching basename and a non-symlink file and parent. It publishes only the existing `stockdata/MU.json` object key, never a source filesystem path. These options reject other directories, path traversal, missing/symlink records and manifest replacement before creating a client; they retain the existing hash delta, upload/retry/failure path and leave unrelated local records out of the upload set. They exist for the named per-stock consumer, not for rewriting a universe from a partial checkout. A narrow candidate preserves every unrelated field from a fresh canonical record, binds its hash and checks that canonical record again immediately before publication. Equal `asof` dates do not make differing local and remote generations interchangeable. Publication still requires actual publisher custody and exact protected-source release. A private producer run is not canonical publication or Portfolio acceptance.

The same native writer exposes `python scripts/stock_liquidity_profile.py --native-adopt MU` for the authenticated stock-artifact consumer. It requires the existing `/var/lock/macro-update.lock`, obtains it without waiting, and qualifies both native and served MU generations before an effect. Each candidate preserves its own unrelated fields and uses the same qualified raw/currency input. Exact pre-publication byte checks protect advancing producers; the existing rsync temporary-file/rename mechanism publishes only those two records. It changes no account, universe, updater or serving configuration. A timeout or unverified write retains `EFFECT_UNKNOWN` with planned hashes rather than retrying. Canonical R2 publication and authenticated native consumption must each be verified separately; neither establishes a sized Portfolio holding or full-book coverage.
