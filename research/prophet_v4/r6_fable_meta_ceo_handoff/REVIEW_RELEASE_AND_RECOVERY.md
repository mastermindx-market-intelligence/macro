# Review, release, recovery and final acceptance

**Accountable program owner: Fable Meta-CEO.** This is an execution contract under the current Chairman delegation, not a new review, incident, runtime or publication system. All delegated reviewers and workers use the existing external fabric. The inherited 126 acceptance entries are requirements, not tests passed in this handoff.

## Independent review sequence

For design, obtain a reviewer who did not author the relevant decision. Give it the exact effective plan digest, changed responsibility/scope, source-bound evidence, prior negative results and question to decide. Ask for concrete contradictions: an undeclared dependency, leaked future knowledge, false action authority, missing source owner, non-discriminating test, or impossible product promise. A reviewer should not receive a request merely to confirm that a long document is impressive.

Fable resolves findings using the same documented input and the decision playbook. A repaired design changes its digest; bind subsequent execution to the accepted revision. The program does not need another Astra decision. A technical owner or regulatory rule that explicitly reserves a particular action still controls that action.

For source, bind the reviewer to exact remote head, actual changed paths and accepted unit. It should review the interface plus the consumer, not only the happy-path new function. It must identify whether purported proof uses a real source/reader or merely mocks the interface it is supposed to prove. State inherited baseline failures rather than suppressing them. An unchanged predecessor's acceptance may be reused by exact reference where still valid; a materially changed head needs fresh affected qualification.

For scientific review, inspect original populations and time cutoffs, registered comparisons, data/model vintages, outcome maturity, effective information, costs and coverage. Challenge target leakage, survivor filtering, horizon selection, double-counted evidence, aliases treated as independent N and repeated peeking. Publication of an impressive result is not a causal explanation, calibration proof, or trade permission.

For UI, review actual user tasks in the shared shell, including dark and light independently, English/Chinese, desktop/mobile, keyboard/focus, contradictory sleeve states and every promised action. A screenshot of a component with simulated authentication must retain that label. Do not count it as an entitled production journey.

## Source and test receipt

The current owner should record repository, source operation, base/head/tree, owned paths, accepted design digest, actual changed capability, test commands/versions and results, inherited failures, review identity/commit/verdict and unresolveds. No fixed tool schema is invented here. Where the owner has a machine receipt, consume it; otherwise record the exact existing GitHub evidence without pretending it is a Runtime status.

Discriminating tests must exercise wrong identity, stale/future evidence, changed source bytes under the same key, missing corporate-action basis, partial/mixed generation, expired/retracted condition, no-entry versus unavailable, and the negative authority boundaries of the specific unit. A zero-row night is legitimate. A forced favorite stock is not an acceptance fixture for market selection.

Use controlled test identities/accounts and obtain scope for external side effects. Do not execute offensive third-party security tests, scrape private provider state, or fetch credentials to fill a missing test. Account-isolation checks stay within approved test accounts and the actual application contract.

## Release phases

### Phase R0 — adopt source, not live authority

Publish the accepted design and exact source change through the current reviewed process. Preserve old versions. Record source merge as a source event only. Feature flags, runtime config and model promotion are separate changes under their own owner. A schema or doc must not silently activate a new strategy.

### Phase R1 — shadow and read-only integration

Prove actual source-to-reader composition, corrections and typed absence. Capture allowed shadow outcomes only under their existing registration. Research views remain visibly research/control. Use the existing flag/runtime mechanisms; do not introduce another experiment or rollout service.

### Phase R2 — bounded entitled-user delivery

Serve the proposed feature to the accepted test or rollout population through current entitlement. Prove actual version/digest, field meanings and real user-action readback. Test denied access and absent optional data. Do not use private vendor data in generated prose when distribution is not licensed.

### Phase R3 — normal refresh and failure recovery

Observe a subsequent ordinary scheduled/source refresh on the same path. It must carry current source/quote clocks and coherent corrected data, preserve user state and exact historical observations, and refuse stale mandatory facts. This is not a one-off manually forced publish disguised as normal operation.

Exercise the accepted rollback plan. Stop the changed model/policy/view using existing controls; preserve old event and grade history. Revalidate current entry facts before showing any restored view. A once-green cached action is not a safe fallback. For an incident, release containment and truthfulness take priority; Fable delegates repair while continuing disjoint safe work.

### Phase R4 — scientific promotion and final claims

Promote only the specific tested model/head/policy and supported population. Include the exact dataset, code, frozen trial, costs, calibration and independent verdict. Model promotion does not release an entry policy or alter held-position management. Claims that exceed evidence stay absent or explicitly experimental.

Fable may authorize an evidence-supported in-scope release through the existing release owner. It cannot grant missing account permissions, override spend or licensing, widen real-money authority, or accept its own code as independently reviewed. It reports a phased launch separately from full program completion.

## Recovery capsule, not transcript replay

At a material boundary, persist the program mission, authority/delegation, adopted spec/source digests, last accepted effects, DO_NOT_REDO, exact unknown effects, current blockers, active child/return refs and next action to the existing owners. Keep one cumulative current frontier; link immutable evidence instead of copying logs. No new model-memory database or event dispatcher is needed.

A new chat or a new provider window does not release source custody or prove interrupted work had no effect. Actual runtime rebinding follows the existing owner. After a reported Thinking failed or repeated substantial session failure, safely reconcile ambiguous writes, persist the frontier and seal that interaction. Resume on a fresh admitted surface from minimum current state, without restarting completed audits.

When a child returns, issue the explicit accepted CONTINUE/REPAIR/HOLD/STOP edge required by the current dialogue procedure. Terminate temporary watchers only when the child is terminal. A named but undelivered worker has no watcher-ready or started status.

For every required capability, bind its actual owner/source/policy/model version, supported population, review, test evidence, deployed path, visual/private-state proof and next ordinary refresh. Include findings that remain negative or underpowered and the exact claims withheld as a consequence.

Show the three initial sleeves and six user jobs as actually served. Show complete candidate visibility without equating board rows, pre-B1 nominations, B1 episodes, featured rows, plans or positions. Show original and current thesis, deterministic entry versus holding decisions, real saved-state behavior and an honest performance record.

Report operating reliability, observed failures, current rollback path and retained legacy controls. Every B00–B28 and Q01–Q24 item needs a disposition; a document, a planned job or a green parent workflow cannot stand in for required capability proof. The added R6 acceptance cases must be covered in addition to the inherited cases, with overlap disclosed.

Fable signs the delegated program conclusion without returning to Astra. A fully supported launch can proceed inside scope; unresolved advertised capability remains an incomplete obligation. Ask the Chairman only for a genuinely reserved authority or material scope decision, not to make routine engineering choices. Do not label the whole mission complete merely because the handoff was complete, infrastructure merged, three sleeves were named, or natural evidence is accruing.
