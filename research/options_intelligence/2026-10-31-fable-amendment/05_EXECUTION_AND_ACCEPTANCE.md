# Execution and acceptance playbook
## One incumbent programme; flexible methods; exact evidence

### 1. Operating intent

Fable owns synthesis, material tradeoffs, programme rulings and final acceptance within its existing commission. Native Opus contributes architecture, scientific judgment, domain supervision and independent challenge where the actual admitted tools permit it. Fabric operators perform bounded research engineering, implementation, repair and verification; operators may self-execute or use optional workers when useful.

The user asked for freedom, so this playbook specifies outcomes and interfaces. It does not prescribe a permanent roster, fixed pool/model, a queue implementation, a maximum number of iterations or a rigid sprint sequence.

Current capability evidence must remain honest: the active ledger's D87 binding gives Fable launch/integration authority and native Opus READ_ONLY advisory windows. The currently queried Fabric adapter reports availability but worker admission/start unprobed, no native parent wake and no background execution. Any broader suborchestrator dispatch role must be established through actual allowed capability, not role naming. [R09](06_EVIDENCE_REGISTER.md#r09) [R52](06_EVIDENCE_REGISTER.md#r52)

### 6. Accept returns by proposition

A useful return states the result first and separates:

- exact source changed;
- tests actually executed by that worker;
- evidence inherited from others;
- independent review and its exact head/scope;
- effects started and their terminal/unknown disposition;
- live consumer proof, if actually performed;
- remaining gaps and the next owner.

“PASS_SCOPED” is not full approval, and parent acceptance of a useful review is not a GitHub approval. A source review can accept a numerical/privacy design while explicitly excluding live roles, migration application and product operation.

When a new head arrives, determine whether changed risk invalidates prior evidence. Re-run only the affected checks or required gate, rather than automatically repeating every historic suite. Respect current required CI and evidence locks; do not change tests to bless drift.

### 7. Acceptance matrix as a static aid

[09_ACCEPTANCE_MATRIX.csv](09_ACCEPTANCE_MATRIX.csv) lists capability assertions, current evidence, a discriminating falsifier and the event that would justify refreshing the row. Its AC labels are document row references only. They are not new task IDs, owners, queues or lifecycle states.

Fable should map a selected assertion into the already adopted task contract and ledger. A single integrated journey can satisfy several assertions when its evidence actually covers them. Conversely, one assertion may require several witnesses because source, privacy and natural-operation claims differ.

Do not count rows as a completion percentage. The value is the specific accepted capability and the remaining critical dependency.

### 8. Review and release

A source patch can be ready for review while release remains held. Before the actual release, the incumbent must possess the concrete integrated artifact, exact head, applicable checks, changed-risk review, effect plan and recovery boundary.

For migrations or retained-reference installation, use the original qualified owner/tool/operation. Preserve preimages, one-use identities, terminal receipts and independent postread where required. An unknown result is reconciled, not replayed through another tool.

For frontend release, verify installed identity before deploying again. Source ancestry is not always sufficient after a squash; use the accepted blob/content checks where the owner contract requires them. A prepared worktree or branch is not a deployment.

The final real-path witness binds source, installed binary/release, account/entitlement, selected population, user actions and observed result. Keep any fixture-controlled negative tests separately labeled. Natural market waits are real dependencies; no fabricated historical visit or forced producer run substitutes for them.

### 9. Continue autonomously without inventing background execution

Within an active authorized session, Fable should keep progressing through useful independent work. A completed leaf is a checkpoint, not an automatic reason to stop. Reassess the next useful outcome and consume pending returns at real boundaries.

Use existing admitted observers for future conditions when the programme already has them. Do not add duplicate polling, cron or watchdog layers. The current adapter's lack of background execution means a web planning turn cannot claim to keep running after it ends.

If a genuine human-only boundary remains—such as an unavailable sign-in, an ungranted credential or a new source purchase—prepare the exact artifact and named next action first. Ask only for that concrete missing act, explain its origin, and continue unaffected work. Do not re-ask already granted permissions or revive a resolved blanket blocker.

### 10. Durable continuation and final closeout

Keep the original ledger and source-bound task tree current at material transitions. Preserve exact accepted evidence, original effects and negative findings. The handoff should let a fresh principal resume the next owned action without replaying the entire 458KB ledger.

A good closeout states:

- the admitted user journeys now accepted, with exact receipts;
- source/release/operational/scientific claims separately;
- remaining unavailable or negative families and what the UI says about them;
- original unresolved effects and their owner;
- what would invalidate the accepted result;
- the next useful goal, or a justified programme closure.

This plan should help Fable finish capabilities. It should not become another artifact that requires a new team merely to interpret it.
