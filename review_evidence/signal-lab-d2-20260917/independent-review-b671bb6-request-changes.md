## MAJOR FINDINGS

**MAJ-1 — The D2 fire rule does **not** reproduce the incumbent on a DVOL calendar gap, while claiming it does.**
`engine/btc_d2_research.py:296` evaluates `btc_impulse_radar._d2_cond(ranges, dvol_w, ranges.index)` — index = the **DVOL** rows. The incumbent (`engine/btc_impulse_radar.py:452`, `:532`) evaluates `_d2_cond(rng, dvol_w, df.index)` — index = the **BTC signals** calendar. `_d2_cond`'s second-confirm branch is `z.shift(1)`, taken *after* the reindex, so `lag1` means "previous BTC day" incumbent-side and "previous DVOL row" research-side. The generation nevertheless stamps `"collector": "btc_impulse_radar._d2_cond.v1"` (`:28`) and `"fire_rule": "z>=2.0 OR (z>=1.5 AND lag1(z)>=1.5)"` (`:159`).
*Failure scenario (reproduced):* 80 daily bars, DVOL missing exactly one day between two 1.7σ range bars, BTC complete. Research → `fired: True`; incumbent `_d2_cond` at the same date → `False` (`z[D]=1.629`, `z[D-2]=1.700`, incumbent's `z.shift(1)` at D is NaN). A Deribit outage of one day is enough; nothing warns.
*Smallest repair:* reindex onto the shared BTC/DVOL calendar before calling `_d2_cond` (pass the BTC `sig` index restricted to `<= source`), or — if the DVOL-row lag is the intended semantic — stop claiming `_d2_cond.v1` and mint a distinct collector version plus an explicit `lag1 = previous DVOL row` in `_spec`.

**MAJ-2 — "Prospective-only" is not enforced; it is an accident of the current call site.**
`engine/btc_impulse_ledger.py:95-107`: enrollment is gated solely on `row_created` (no row with that `asof` exists). Nothing compares the observation date to the recording clock. `lifecycle.recorded_at` (`btc_d2_research.py:43-46, 62`) is deliberately excluded from identity, is never validated, never projected (`project()` at `:482-531` drops it), and never rendered.
*Failure scenario (reproduced through the module's public API):* `LED.stamp(radar{asof: 2024-03-03}, full_tape, dvol_df=…, recorded_at="2026-09-17T05:00:00Z")` followed by `LED.grade(full_tape, recorded_at="2026-09-17T05:00:01Z")` mints and matures a journey **in the same second, two years after the fact**, and Signal Lab renders it as `Prospective research journey … Matured · down target hit`. Both generations carry a 2026-09-17 `recorded_at` and nothing rejects them.
*Reachability, stated honestly:* the one production caller passes the **same** frame to `stamp` and `grade`, and `radar["asof"] = df.index[-1]` (`btc_impulse_radar.py:492`), so same-run maturation is currently unreachable there. The boundary is defended by a coincidence of the call site, not by the contract. Existing legacy rows — including same-`asof` ones — *are* correctly protected and tested (`tests/test_btc_d2_research_journey.py:376-407`).
*Smallest repair:* in `stamp`, refuse to mint `research_d2` when `row["asof"]` is older than `date(recorded_at or utcnow())` by more than the permitted build lag; leave the row itself unenrolled, exactly as a legacy row.

**MAJ-3 — A non-firing matured observation renders a factually false outcome line.**
`templates/signal_lab.html.j2:290-296` branches only on `journey.outcome.down_hit`, but `down_hit` is `bool(fired and fwd_min <= -LABEL_THR)` (`btc_d2_research.py:445`) — it is forced `False` whenever the raw observation did not fire, regardless of the tape.
*Failure scenario (reproduced render):* `fired=False`, forward closes 98/94/93 → the d2 cell prints `Raw D2 observation: did not fire … Matured · down target missed · -7.0% / -2.0%` (and `已成熟 · 下行目标未命中`). The declared target is −5%; the move was −7%. Both language columns assert a miss beside a number that exceeded the target.
*Smallest repair:* add a third branch — when `journey.fired` is not `true`, render `Matured · not graded (no fire)` / `已成熟 · 未触发，不计命中` and keep the `fwd_min/fwd_max` pair as context.

**MAJ-4 — The "corrected" state is invisible on the surface the mission requires it to appear on.**
`project()` (`btc_d2_research.py:482-531`) returns only the *effective* source/outcome plus a bare `generation_count`; it exposes no `corrected` flag, no correction `reason` (`late_source_arrival` / `source_restatement` / `outcome_input_restatement`), and no superseded-generation ids. The template surfaces that as one integer (`:281-282`, "Immutable generations: N").
*Failure scenario:* an outcome restatement flips `down_hit` from `true` to `false` (exactly the path `tests/…:189-203` exercises). The page silently changes from "down target hit" to "down target missed"; the only visible difference is `Immutable generations: 2` → `3`, which a reader cannot distinguish from a late source arrival or from a second unrelated generation. An append-only correction chain whose corrections are unreadable delivers the storage property but not the product outcome ("append-only correction generations … appear in Signal Lab as research-only context").
*Smallest repair:* have `project()` emit `corrections: [{target_kind, reason, supersedes_generation_id}]` and `corrected: bool`, and render one line — "Restated N× (source restatement)" / "已修订 N 次（来源重述）".

**MAJ-5 — The research-only journey can take down the incumbent ledger summary.**
`_canonical` uses `allow_nan=False` (`btc_d2_research.py:36`), so `_digest` raises a bare `ValueError` on a non-finite float. `project()` catches only `GenerationConflict` (`:500-504`), which is a *subclass* — a bare `ValueError` escapes. `btc_impulse_ledger.latest_d2_journey` (`:168-176`) is unguarded, and `render_summary` (`:190`) now calls it unconditionally.
*Failure scenario (reproduced):* one row whose `research_d2` contains a NaN (persisted verbatim, because `_write` uses `json.dumps` with default `allow_nan=True` and `load` parses the bare `NaN` token back) makes `render_summary()` raise and `grade()` return `{'ok': False, 'reason': 'ValueError: Out of range float values are not JSON compliant: nan'}`. The entire incumbent forward hit-rate summary — `n_rows`, `n_matured`, `down.hit_rate`, `up.hit_rate`, the falsifier tape — is lost and published as `regime["impulse_ledger"] = {ok: False}` (`scripts/build_vector.py:4225`). This regresses the invariant the incumbent states in-file ("one corrupt/hand-edited row must NOT abort grading of every other row") from row-scoped to whole-summary-scoped, and it is precisely the non-goal: a research-only addition degrading the incumbent. (The delta *also* hardened the sibling path — `row["fires"]` → `row.get("fires", {})` — so this is a new vector, not a net wash.)
*Smallest repair:* catch `(GenerationConflict, ValueError, TypeError)` in `project()` and return `reason="generation_integrity_error"`; wrap `latest_d2_journey`'s per-row `project` call in the same guard.

**MAJ-6 — Immutability is tamper-evident against in-place edits only; truncation and rollback are undetectable, over a non-atomic unlocked store.**
Generations are content-addressed individually (`make_generation`, `:53-63`) but the *list* is not chained: a `source` carries no predecessor link, and dropping the last N generations leaves a journey that passes `_validate_journey` unchanged. Underneath it, `_write` (`btc_impulse_ledger.py:56-59`) is a full-file `write_text` with no temp-file + `os.replace` and no lock, and `load` (`:42-54`) silently `continue`s past any line that fails `json.loads`.
*Failure scenario:* a crash, ENOSPC, or a concurrent writer during the rewrite truncates the file; `load()` drops the malformed tail line without a word, and every frozen generation in it is gone — while every surviving journey still validates and still reports `Immutable generations: N`. Measured payload today: **7,944 bytes per source generation** (real frames), so the file that is rewritten in full each night grows ~8 KB per enrolled row; the rewrite window is materially wider than pre-delta.
*Smallest repair:* make `_write` atomic (`tmp = p.with_suffix(".tmp"); tmp.write_text(...); os.replace(tmp, p)`), and include `prev_generation_id` in each generation's identity payload so a truncated tail is detectable.

## CORRECTION / IMMUTABILITY ASSESSMENT

**What holds.** Generation identity binds `{kind, semantic}` under a canonical, sorted, separator-fixed JSON digest (`:35-40, :53-63`) and correctly excludes `lifecycle.recorded_at` — verified by the round-trip probe and by `tests/…:61-82`. The semantic payload binds every material input (all 62 DVOL rows with their `asof`, the entry close, the `source_digest`), the evaluator and collector versions, the spec (window, fire rule, horizon, threshold, `trading_authority`), the source↔outcome relationship (`source_generation_id`), and — for corrections — `target_kind`, `supersedes_generation_id`, `reason`, and the full `replacement`. `_validate_journey` (`:66-126`) rejects malformed envelopes, unknown kinds, duplicate identities, a second source root, an orphan outcome, an outcome that silently replaces another, and any correction that does not supersede the *current* head; `append_generation` (`:129-148`) validates the journey, verifies the claimed digest, dedupes identically, raises on a same-id/different-semantics collision, and — correctly — validates a **candidate copy** before mutating. Floats survive the JSON round trip exactly, so `current_semantic == candidate` comparisons after reload are stable. A source correction correctly resets the outcome epoch (`:94, :116`), forcing re-maturation rather than silent carry-over. The three erasure vectors the mission names are all handled: a later feed outage cannot supersede a frozen `available` source (`:384-385`, the `b671bb6c` fix, pinned by `tests/…:331-344`); a late arrival appends rather than rewrites (`tests/…:126-156`); a close restatement appends an outcome correction and the original survives (`tests/…:189-203`).

**What does not hold.** Tamper-evidence covers in-place mutation of a *retained* generation only. Deletion, truncation, and rollback produce a shorter journey that validates cleanly (MAJ-6), the store underneath is a non-atomic unlocked full-file rewrite that silently drops unparseable lines, and the one datum that would distinguish a genuinely prospective record from a retrofitted one — `recorded_at` — is deliberately outside identity and is never checked or shown (MAJ-2). Corrections are stored immutably and then hidden from the reader (MAJ-4).
